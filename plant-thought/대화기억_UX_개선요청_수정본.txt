기존 Personal Memory Agent / Plant Thought 앱의 화면 구성과 스타일을 유지하면서, 상황별 작업 버튼만 필요한 위치에 추가하고 아래 기준에 따라 대화·기억 조회·저장·수정의 처리 로직을 개선해줘.

설명이나 계획 제시로 끝내지 말고 기존 코드를 확인하고 구현·검증까지 진행해줘.

## 1. 작업 범위

- 기존 화면 구성, 레이아웃, 색상, 글꼴, 여백, 크기, 아이콘, 말풍선 스타일, 사이드바, 달력, 반응형 디자인을 변경하지 않는다.
- 정적인 제목·소개 문구도 변경하지 않는다.
- 수정 대상은 입력 해석, 대화 맥락 유지, 기억 검색, 근거 판단, 응답 내용, 확인·취소, 저장·수정 상태 처리다.
- 안내와 변경 전·후 내용은 기존 대화 말풍선에 표시한다.
- 화면에 추가할 수 있는 요소는 상황별 작업 버튼뿐이다. 기존 말풍선 아래 작업 버튼 영역과 기존 버튼 스타일을 재사용한다. 버튼 표시로 필요한 최소 높이 증가는 허용하되 화면 구획·기존 간격 규칙을 재설계하지 않는다.
- 저장 확인: 기록하기/취소. 수정 확인: 수정 반영/취소. 오류: 다시 시도. 근거 확인: 기록 열기. 실제 추가 조회가 가능한 경우에만 추가로 찾아보기를 표시한다.
- 동명이인·사건 확인에는 실제 후보의 구분 단서를 버튼으로 표시할 수 있다. 학교 관련 기록/회사 관련 기록 선택은 이번 질문의 범위를 좁힐 뿐, 인물의 동일성·별개성을 영구 저장하지 않는다.
- 일반 답변마다 버튼을 일괄 추가하지 않는다. 사용자의 선택이나 후속 행동이 필요한 순간에만 표시한다.
- 버튼 선택과 자연어 응답은 같은 처리 로직을 사용한다. 선택한 의미를 현재 대화에 남겨 후속 질문에서도 해석할 수 있게 한다.
- 후보가 많으면 기존 버튼 영역이나 자연어 확인 질문 하나를 이용한다. 새 선택 창·패널을 만들지 않는다.
- 버튼에는 명확한 이름을 제공하고 키보드 조작과 작은 화면 동작을 유지한다. 중복 클릭과 종료된 작업의 과거 버튼 재실행을 막는다.
- 새로운 페이지, 검토 화면, 사례 탐색기, 설정 패널, 배너를 만들지 않는다.
- 새 검증 사례와 예시 대화를 실제 사용자 기록이나 대화 내역에 자동 삽입하지 않는다. 분리된 테스트 저장소와 대화 세션에서 사용한다.
- 사용자가 이미 요청해 저장한 [테스트] 가상 기록 10개는 유지한다. 이를 삭제·덮어쓰기하거나 이번 검증 사례를 자동 추가하지 않는다.
- 실제 앱이 사용하는 코드·API·저장소를 먼저 확인하고 수정 대상 경로를 명시한다. 별도 시연 코드를 실제 처리 경로로 착각하지 않는다.
- 현재 화면용 M1 연결 코드와 이전 다조건 평가 코드의 구현 범위 차이를 확인한다. 새 서버나 저장소로 대체하면서 기존 기능·설정이 빠지게 하지 않는다.
- 기존 모델·기억 방식·검색 방식·Top-K·후보 선택·답변 방식·프롬프트의 실험 설정을 임의로 변경하거나 한 값으로 덮어쓰지 않는다.
- 실험 조건을 선택하는 새 화면·설정 패널은 만들지 않는다. 현재 코드에 없는 실험 경로의 통합이 필요하면 별도 미구현 항목으로 보고한다.
- 기존의 정상적인 저장·검색·기록 열기 기능을 유지한다.
- `sources/` 아래의 동기화된 참조 파일은 수정하지 않는다.

## 2. 입력과 대상 해석

다음 항목을 구분해서 처리한다.

- 입력 의도: 기억 조회 / 기록 저장 / 수정 / 감정 공유 / 일반 질문 / 불명확
- 질문 대상: 명확 / 앞 대화로 연결 가능 / 여러 후보 / 확인 불가
- 동명이인: 한 명으로 식별 / 같은 이름의 여러 사람 / 구분 단서 부족
- 별명·호칭: 연결 근거 있음 / 연결 근거 없음
- 질문 범위: 한 가지 / 여러 하위 질문 / 범위 불명확

처리 원칙:

- 최근 대화로 대상을 해석할 수 있으면 불필요한 재확인 없이 이어간다.
- 이름이 같다는 이유로 인물 기록을 합치지 않는다.
- 직장·학교 등 소속이 다르다는 이유만으로 반드시 다른 사람이라고 확정하지도 않는다.
- 별명과 본명은 연결 근거가 있을 때만 같은 사람으로 취급한다.
- 이번 질문에서 대상을 좁히는 것과 영구적인 인물 관계를 저장하는 것을 구분한다.
- 불명확하면 후보를 구분하는 단서 한 가지만 묻는다.
- 사용자가 찾으려는 정답 자체를 대신 알려 달라고 묻지 않는다.
- 복합 질문은 하위 질문별로 처리한다. 일부만 확인되면 확인된 부분을 먼저 답하고 부족한 부분을 구분한다.

예:
“민수랑 부산 갔어”가 저장 요청인지 불분명하면 임의 저장하지 않고 “이 내용을 새 기록으로 남길까요?”라고 확인한다.

## 3. 기억과 근거 판단

다음 상태를 구분한다.

- 근거 충분성: 충분 / 일부만 있음 / 확인할 근거 없음
- 검색 범위: 필요한 범위 조회 완료 / 일부 후보만 조회 / 조회 실패
- 표현 차이: 원문 표현 일치 / 같은 의미의 다른 표현 / 연결 불확실
- 부정 여부: 명시적 긍정 / 명시적 부정 / 언급 없음
- 기록 충돌: 내용 일치 / 명시적 정정 / 서로 다른 주장 / 구분 불가
- 접근 범위: 현재 조회 가능 / 삭제·권한 제한·저장 제외
- 근거 중복: 독립된 기록 / 복제·재요약 / 관계 불명확
- 처리 오류: 정상 / 서버·모델·검색 오류

처리 원칙:

- 현재 설정된 검색·답변 경로를 유지하면서, 현재 접근 가능한 기록으로 뒷받침되는 범위까지만 답한다.
- 원문·발췌·생성 요약 중 실제 사용한 근거 종류를 구분해 연결한다. 요약 인용을 원문 직접 인용으로 표시하지 않는다.
- 원문 구간 확인이 필요하면 해당 구간과 버전을 확인한다. 이 요구를 원문 전체를 모델에 넣는 별도 검색·답변 방식으로 임의 변경하지 않는다.
- 이전 AI 답변을 사실의 근거로 재사용하지 않는다.
- Top-K 등 일부 후보에서 찾지 못했다는 이유로 전체 기억에 없다고 단정하지 않는다.
- 추가 조회가 가능하면 필요한 범위를 더 확인한다. 불가능하면 확인한 범위를 명시한다.
- “독서”와 “책을 읽었다”처럼 의미가 같은 표현은 연결하되, 비슷한 단어만으로 같은 사건이라고 판단하지 않는다.
- 언급이 없다는 것과 명시적으로 하지 않았다는 것을 구분한다.
- 정정 대상이 명확한 기록만 정정 관계로 연결한다.
- 해결되지 않은 충돌은 양쪽 주장과 근거를 제시한다. 최신 작성일이라는 이유만으로 하나를 정답으로 선택하지 않는다.
- 복제·재요약된 기록 수를 독립적인 사실 확인 횟수로 세지 않는다.
- 삭제·권한 제한·저장 제외 이후의 검색·답변·인용·캐시 재사용과 앱 안의 이전 대화 재표시에서 현재 접근 상태를 확인한다. 출처·버전 연결을 유지한다. 접근 불가능한 내용의 존재도 불필요하게 드러내지 않는다.
- 이미 사용자가 읽거나 별도로 복사한 정보를 회수했다고 주장하지 않는다.
- 현재 서버가 지원하는 사용자·삭제·버전·접근 범위를 검증한다. 계정·공유 기능이 없는 구성에 새 인증·권한 관리 화면을 만들지 않는다. 권한 변경은 분리된 서버 범위 테스트로 확인하고 실제 계정 간 권한 검증과 구분한다.
- 접근 제한은 실제 서버 조회와 응답 생성 단계에서 적용한다. 화면에서 숨기는 것으로 대체하지 않는다.
- 오류를 “기억에 없음”으로 바꾸지 않는다.

아래 문구의 의미를 반드시 구분한다.

1. 조회한 근거에서 미확인:
   “찾은 기록에서는 숙소 이름을 확인하지 못했어요.”

2. 일부만 확인:
   “지수와 부산에 간 것은 확인되지만 숙소는 확인되지 않아요.”

3. 조회 자체 실패:
   “기록을 조회하지 못했어요. 다시 시도해 주세요.”

4. 일부 후보만 확인:
   “이번에 확인한 일부 기록에서는 숙소 이름이 나오지 않았어요. 아직 필요한 범위를 모두 조회한 것은 아니에요.”

## 4. 날짜와 사건 해석

다음 상태를 구분한다.

- 날짜 해석: 명시 날짜 / 상대 날짜 / 여러 날짜 / 불명확
- 날짜 역할: 기록 작성일 / 사건 발생일 / 예정일
- 사건 진행: 계획 / 변경 / 진행 / 완료 / 취소 / 확인 불가
- 변경 순서: 이전 값 / 변경 값 / 실제 결과 / 순서 불명확
- 사건 동일성: 같은 사건 / 별개 사건 / 연결 불확실

처리 원칙:

- 상대 날짜는 실제 요청 시각과 앱이 지원하는 사용자 시간대로 계산한다. 기존 기본 시간대를 유지하고 새 시간대 설정 화면은 만들지 않는다.
- 자정·월말·연말 검증의 고정 시각은 테스트 환경에서만 주입한다. 운영 코드에 시연용 기준 날짜를 하드코딩하지 않는다.
- 작성일·사건일·예정일을 혼동하지 않는다.
- 기록에 없는 사건 날짜를 작성일로 채우지 않는다. 날짜 미지정 저장의 기본 기록일을 오늘로 정하는 것과 사건 발생일을 추정하는 것을 구분한다.
- 계획을 실제 발생으로 바꾸지 않는다.
- 완료 보고가 없다는 이유로 미완료라고 확정하지 않는다.
- 최초 계획 → 변경 계획 → 실제 결과를 구분한다.
- 인물·장소·날짜가 일부 겹쳐도 별개 사건을 자동 병합하지 않는다.
- 날짜 후보가 여러 개면 구분에 필요한 시기 단서 하나만 묻는다.

## 5. 대화 흐름과 정정

구분할 상태:

- 후속 질문: 이전 대상 유지 / 대상 변경 / 대상 불명확
- 주제 전환: 같은 주제 / 명시적 전환 / 새 대화
- 사용자 정정: 이번 대화의 정정 / 저장 기록 수정 요청 / 정정 대상 불명확

처리 원칙:

- “그 사람”, “그때”는 현재 대화에서 해석한다.
- 주제가 바뀌면 이전 사건의 인물·장소를 새 주제로 끌고 가지 않는다.
- 새 대화는 이전 대화의 대상·임시 정정을 자동 상속하지 않는다.
- “민수가 아니라 지수였어”는 정정할 사건이 분명할 때 이번 대화에 반영한다. 대상이 여러 개면 사건부터 확인한다. 원문을 수정했다고 안내하지 않는다.
- 임시 정정은 사용자가 이번 대화에서 알려준 내용으로 구분한다. 기존 기록이 그 정정을 뒷받침한다고 잘못 인용하지 않는다.
- 저장 기록 수정 요청이 명확할 때만 수정 절차로 이어간다.
- 수정 대상이 모호하면 대상 하나를 확인한다.
- 사용자의 현재 정정과 기존 저장 기록의 주장을 구분해 표현한다.

## 6. 저장·수정·취소

저장 의사를 다음과 같이 구분한다.

- 명시적 저장 요청
- 확인 대기
- 취소
- 요청 없음

처리 원칙:

- 조회·감정 공유·일반 질문을 임의로 기록에 저장하지 않는다.
- 저장이나 수정에 확인이 필요하면 기존 대화 안에서 대상과 내용을 보여준다.
- 수정은 기존 말풍선에 대상 기록·변경 전·후를 표시하고 수정 반영/취소 버튼으로 확인할 수 있게 한다.
- 수정은 기록 식별자와 확인한 버전에 연결한다. 확인 이후 기록이 바뀌면 덮어쓰지 말고 최신 내용을 다시 확인한다.
- 사용자가 이미 내용과 대상을 명확히 확인했다면 같은 확인을 반복하지 않는다.
- 예/아니/취소와 확인 버튼은 현재 대화의 유효한 작업 식별자·대상·확인 내용에만 연결한다. 주제 전환이나 새 대화의 응답을 이전 저장 동의로 사용하지 않는다.
- 확인 대기 중 독립적인 새 질문이 들어오면 이전 저장 승인으로 해석하지 않는다. 미완료 작업을 보류·취소·재확인하되 저장 여부 미결정을 이유로 모든 대화를 막지 않는다.
- 실제 저장·수정 성공이 확인된 뒤에만 완료를 알린다.
- 처리 중 중복 제출을 방지한다.
- 실패하면 내용을 유지하고 재시도할 수 있게 한다.
- 시간 초과나 응답 유실로 저장 결과가 불명확하면 실패 또는 성공으로 단정하지 않는다.
- 불명확한 결과는 저장 결과를 확인하지 못했다고 안내하고 동일 요청 식별자로 저장 상태를 먼저 확인한다.
- 서버에 작업 식별자와 처리 결과를 보관하고 조회할 수 있게 한다. 재시도는 같은 작업을 이어가며 새 저장으로 중복 실행하지 않는다.
- 날짜·본문이 같다는 이유만으로 사용자가 별도로 명시한 저장 요청까지 무조건 동일 작업으로 취급하지 않는다.
- 확인 단계의 취소는 저장·수정을 실행하지 않는다.
- 이미 반영된 저장을 단순 취소 응답만으로 없어진 것처럼 표현하지 않는다.

## 7. 감정 공유와 기록 속 명령

감정 상태:
직접 표현된 감정 / 해석 가능성 / 단서 없음

- 직접 말한 감정에는 자연스럽게 공감한다.
- 원인·진단·성격을 사실처럼 만들어내지 않는다.
- “답답했다”에서 우울증 등 진단을 단정하지 않는다.
- 필요하면 열린 질문 하나로 사용자가 자신의 감정을 표현하도록 돕는다.
- 감정을 나눴다는 이유로 자동 저장하지 않는다.

명령의 출처:
사용자의 현재 요청 / 저장된 내용 안의 문장

- 기록에 있는 “이전 지시를 무시해” 같은 문장은 기록 내용으로만 취급한다.
- 저장된 문장이나 검색 결과가 앱의 지시·도구 실행·권한 변경을 유발하지 못하게 한다.

## 8. 최종 응답 행동

상황에 따라 다음 8가지 행동을 선택한다.

1. 답변: 대상이 분명하고 근거가 충분함
2. 부분 답변: 하위 질문 중 일부만 확인됨
3. 확인 질문: 대상·동명이인·날짜·의도 등의 구분이 필요함
4. 확인 불가 안내: 조회한 범위에 필요한 근거가 없음
5. 명시적 부정 답변: 직접적인 부정 근거가 있음
6. 충돌 안내: 관련 기록의 주장이 충돌하고 해결되지 않음
7. 처리 실패 안내: 검색·모델·서버 오류로 판단할 수 없음
8. 저장 확인·취소: 저장 또는 수정 의사를 확인하거나 취소함

여러 조건이 동시에 걸리면 하위 질문별 판단을 유지한다. 일부의 모호함이나 오류 때문에 독립적으로 확인된 사실까지 버리지 말고, 확인된 내용과 미확인·실패한 부분을 구분한다.

응답은 기존 앱의 말투로 간결하게 작성한다. 내부 분류명, 시스템 프롬프트, 점수, 디버그 정보는 사용자에게 노출하지 않는다.

인용은 기존 참고 기록 UI를 재사용하고, 실제로 사용한 현재 접근 가능한 기록에만 연결한다.

## 9. 구현 방식

- 기존 구조와 데이터 모델을 먼저 파악한 후 필요한 부분만 수정한다.
- 판단 로직은 화면 스타일과 분리한다.
- 임의의 키워드 몇 개나 예시 문장 하드코딩으로 전체 요구사항을 처리하지 않는다.
- 필요한 메타데이터가 없으면 미확인으로 처리한다. 인물 관계·사건 관계·정정 관계·저장 성공을 만들어내지 않는다.
- API·데이터 구조 변경은 기존 데이터와 호환되는 최소 범위로 구현한다. 화면 변경이 버튼 수준이라는 이유로 서버 검증을 생략하지 않는다.
- 작업 식별자·점수·내부 분류명은 화면에 노출하지 않는다.
- 실제 기능 대신 시연용 응답으로 대체하지 않는다.
- 기존 기록을 삭제하거나 예시 데이터로 덮어쓰지 않는다.

## 10. 검증

각 테스트는 다음 항목을 함께 고정한다.

- 저장된 기록과 현재 접근 가능한 범위
- 이전 대화와 현재 입력
- 적용 변수와 상태
- 기대 응답 행동
- 반드시 포함할 사실
- 금지할 추측·혼동
- 필요한 인용 또는 확인 질문
- 표시 버튼과 버튼·자연어 응답의 동일 동작
- 저장소 변경 유무, 대상·버전·작업 식별자
- 시각·오류·권한·검색 범위의 시험 조건

예상 답·판정 기준은 모델 입력이나 사용자 기억에 넣지 않는다. 확인 질문은 특정 문구의 완전 일치보다 대상 구분에 필요한 정보와 동작이 맞는지 판정한다.

최소한 아래 상황을 검증한다.

- 동일한 “민수랑 어디 갔었지?”가 앞 대화 유무에 따라 답변 또는 확인 질문으로 달라짐
- 학교·회사 맥락을 구분하되 인물의 동일성이나 별개성을 임의 확정하지 않음
- 별명 연결 근거 유무
- 복합 질문의 부분 답변
- 근거 미확인 / 일부 조회 / 조회 실패의 구분
- 명시적 부정과 미언급의 구분
- 명시적 정정과 미해결 충돌의 구분
- 삭제·권한 변경 후 이전 답변과 인용을 통한 재노출 방지
- 복제 기록을 독립 근거로 중복 계산하지 않음
- 시간대·자정·월말·연말 기준 상대 날짜
- 작성일·예정일·실제 진행일의 구분
- 주제 전환과 새 대화의 맥락 분리
- 대화 중 정정과 저장 원문 수정의 구분
- 감정 공유의 자동 저장 방지
- 확인 전 취소, 저장 성공, 저장 실패, 응답 유실, 재시도 중복 방지
- 기록 속 명령이 실행되지 않음
- 복합 질문에서 일부만 모호하거나 실패한 경우
- 기존 화면 구성·스타일·정적 문구·주요 기능 유지
- 버튼의 실제 대상 연결, 키보드 조작, 중복 클릭, 종료된 작업 재실행 방지
- 버튼과 자연어 응답의 동일 결과
- 수정 확인 도중 다른 변경이 발생하면 오래된 버전 덮어쓰기 방지

테스트 통과를 실제 모델의 모든 응답이나 모든 변수 조합에 대한 보증으로 표현하지 않는다.

자동 기능 검사, 실제 모델 실행, 답변 의미 검토를 분리해 보고한다. 미실행 사례와 미지원 조건을 통과로 세지 않는다.

작업 완료 후 변경 동작·수정 파일·검증 결과·제한사항을 알려줘. 기존 화면 구성·스타일의 유지 여부와 추가한 상황별 버튼을 구분해 보고해줘.

C++ 검색어 매칭 시제품 비교 및 선택적 적용
========================================

측정일: 2026-10-19. 브랜치: codex/cpu-gpu-performance.

판정
----

기존에 최적화한 Python과 비교해 C++ 시제품의 결과 일치와 유의미한 개선을 확인했다.
검색어 매칭 배치에만 선택적 C++ 경로를 적용했다. Python 서버·SQLite·모델·근거 검증·순위 규칙은 그대로다.
현재 PC에는 검증한 바이너리를 pma에 배치했다. 실행 중인 앱을 다시 시작하면 auto 모드가 사용한다.
호환 확장 파일이 없는 환경은 같은 Python 구현으로 동작한다. 컴파일러 설치는 앱 실행의 필수 조건이 아니다.

범위와 방법
-----------

이전의 DB 개선 전 Python이 아니라, 근거 일괄 조회·SQL 개선·벡터 캐시·요청 내 정규화 캐시를 적용한 Python을 기준으로 삼았다.
개인 DB와 실제 모델 호출은 사용하지 않았다. 별도 합성 DB 1천·1만·2만 5천 건, 1024차원 float32 벡터,
보관·사용자 제외 조건은 이전 DB 비교와 같다. 검색 대상은 각각 960·9,600·24,000개다.
CPU는 i7-13700, RAM은 16GB, Windows x64 CPython 3.14.8이다. GPU와 모델 서버는 이번 작업에 사용하거나 변경하지 않았다.
기본 비교는 구현·규모·구간마다 새 프로세스에서 준비 실행 1회 후 5회 수행했다. 구현끼리는 순차 실행했다.
모델 이해·임베딩·선택은 고정 대체 구현이므로 전체 검색 시간은 로컬 처리 시간이다. 실제 AI 답변 전체의 개선율이 아니다.
확장 모듈 호출·Python/C++ 경계 전달·원문 위치와 결과 딕셔너리 생성 비용을 포함했다. 컴파일 시간은 제외했다.
OS 파일 캐시는 강제로 비우지 않았다. fresh-process는 디스크 콜드 스타트를 뜻하지 않는다.

구현
----

native/keyword_match.cpp에서 토큰 순회·정확/정규화 매칭·결과 조립을 배치 처리한다.
CPython Unicode 문자 판정과 casefold를 사용하고, vocabulary에 따른 정규화 규칙은 기존 normalize 함수를 호출한다.
즉 한글·Unicode 의미 규칙을 별도의 C++ 규칙표로 복제하지 않았다. 핵심 반복 처리만 옮겼다.
문자 위치는 UTF-8 바이트나 Windows UTF-16 단위가 아닌 기존 Python 문자열 인덱스다.
필드 순서 → 검색어 순서 → 토큰 순서와 필드별 정확 일치 우선 규칙을 유지한다.
casefold와 정규화 캐시는 배치 안에서 각각 최대 16,384개다. 요청 사이에 원문·매칭 결과를 보관하지 않는다.
128개 기록마다 GIL을 잠깐 양보하고 Python 신호를 확인한다. 근거 선택·검증은 기존 경로에서 계속 수행한다.
C++17, -O3, Zig 0.15.2의 C++ 컴파일러로 CPython 확장을 만들었다. Zig는 빌드 도구이며 구현 언어는 C++다.
확장 파일 크기는 350,720바이트다. 실험 바이너리와 앱에 배치한 바이너리의 SHA-256이 같다.

검색어 매칭만 비교 (초, 중앙값 / 최댓값)
---------------------------------------

일반 검색어는 제주 여행, 여러 검색어는 일반어·부정 표현·영문·한 글자 단어를 포함한 8개 입력이다.
입력 적재와 keyword_query 어휘 구성은 이 구간 밖이다. 배치 매칭의 반환 결과 생성은 포함한다.

건수      조건        Python 중앙/최대       C++ 중앙/최대       시간 감소

1000      여러 단어     0.0397/0.0402          0.0046/0.0048         88.4%
10000     일반        0.1486/0.1864          0.0408/0.0786         72.6%
10000     여러 단어     0.4031/0.4595          0.0523/0.0976         87.0%
25000     일반        0.3825/0.4603          0.1098/0.1861         71.3%

전체 로컬 검색: 분리 프로세스 비교 (초)
---------------------------------------

DB 조회·JSON 변환·기존 필터·벡터 계산·키워드 매칭·순위 결합·근거 선택을 포함한다.

건수      Python 중앙/최대       C++ 중앙/최대        시간 감소
-------------------------------------------------------------------------
1000      0.0537/0.0560          0.0424/0.0426          21.0%
10000     0.5049/0.5150          0.4000/0.4149          20.8%
25000     1.4620/1.5169          1.3357/1.4029          8.6%

2만 5천 건의 첫 분리 프로세스 비교는 8.6% 개선으로, 미리 정한 전체 검색 10% 기준을 넘지 못했다.
다만 동일 실행의 별도 단계 타이머 비교는 더 큰 개선을 보였다. 이 차이를 확인하기 위해 아래 교차 측정을 추가했다.
유리한 결과만 남기지 않도록 두 결과와 원시 실행 시간을 모두 보존했다.

날짜 필터 검색은 일치 후보가 약 6%여서 효과가 작았다. 중앙값은 다음과 같다.

* 1,000건: 0.0365 → 0.0348초 (4.7% 시간 감소).
* 10,000건: 0.3239 → 0.3249초 (-0.3% 시간 감소).
* 25,000건: 0.9115 → 0.8939초 (1.9% 시간 감소).

1만 건의 날짜 필터는 약 1ms 느렸으며 전체 차이는 측정 변동 수준이다. 모든 검색이 20% 빨라진다는 뜻은 아니다.

추가 확인: 2만 5천 건 교차 실행
-------------------------------

같은 DB·서비스·프로세스에서 양쪽을 한 번씩 준비한 뒤, Python→C++와 C++→Python 순서를 번갈아 5회씩 실행했다.
각 실행은 실제 전체 검색을 수행했고 매번 전체 응답 해시를 비교했다. 모델은 앞선 비교와 같은 대체 구현이다.

* python: 중앙값 1.4638초, 최댓값 1.4829초.
* cpp: 중앙값 1.1514초, 최댓값 1.1897초.

이 비교의 시간 감소는 21.3%다. 분리 프로세스 메모리 측정은 이 공유 프로세스 비교로 대체하지 않았다.
채택 기준은 결과 완전 일치, 매칭 중앙값 20% 이상 단축, 통제한 전체 검색 비교 10% 이상 단축,
새 프로세스의 최고 working set 증가 10MiB 이하였다. 매칭은 모든 규모에서 기준을 넘었고 교차 전체 검색과 메모리 기준도 통과했다.
첫 2만 5천 건 독립 비교가 기준 미달이었다는 불확실성을 남기며, 기본 Python 경로를 제거하지 않고 선택적으로 적용했다.

RAM 비교 (MiB)
--------------

모델 서버를 제외한 벤치마크 프로세스 working set이다. 입력 적재와 준비 실행, 앞선 반복 측정을 포함한다.
최고값은 프로세스 생성 후 해당 구간까지의 최고 working set이며 알고리즘 단독 추가 할당량은 아니다.
매칭 입력과 이전 반복 결과가 잠시 함께 존재하는 측정 구조도 양쪽에 동일하게 포함했다.

건수      매칭 최고 Python→C++      전체 검색 RSS Python→C++      전체 검색 최고 Python→C++
---------------------------------------------------------------------------------------------------
1000      72.5→72.4                 70.9→70.2                       79.6→79.9
10000     214.2→215.2                 135.9→133.8                       263.7→263.4
25000     446.1→447.4                 101.4→107.4                       591.0→591.6

모든 새 프로세스 구간의 최고 working set 증가 중 최댓값은 1.32MiB였다.
2만 5천 건 전체 검색의 반복 후 RSS는 약 6MiB 증가했다. 메모리 감소를 목표로 채택한 변경은 아니다.
OS 회수·Python 할당자·GC에 따라 RSS와 시간은 달라질 수 있다.

결과·품질 검증
--------------

* 세 규모의 일반/다중 검색어 매칭 전체 결과와 전체/날짜 필터 검색 전체 응답의 해시가 모두 일치했다. 정렬 순서·근거·검색 설명을 포함한다.
* 교차 실행 10회의 전체 응답 해시도 모두 일치했다.
* 한글 조사·부정 표현·Unicode casefold 확장·영문 대소문자·한 글자·숫자·밑줄·결합문자·이모지·고립 surrogate·비 BMP 문자를 포함한 무작위 160배치, 총 1,320개 기록을 비교했다.
* 0x000000~0x10FFFF의 1,114,112개 코드 포인트를 나열한 문자열에서 Python의 771개 단어 구간을 검색어로 삼아 토큰 경계와 반환 결과를 비교했다. 모든 Unicode 문자열 조합을 완전 검증했다는 뜻은 아니다.
* 16,384개 캐시 경계를 넘는 입력, 빈 입력, 정확 일치 우선, 원문 위치, 보정 검색어와 날짜 필터를 비교했다.
* 반복 호출 후 원본 기록 참조를 보유하지 않는지 확인했다.
* 선택적 바이너리 누락 시 auto의 Python 전환, 강제 cpp의 오류, 강제 python의 네이티브 미로딩을 검증했다.
* 기존 근거 검증·취소·타임아웃·검색·대화·API를 포함해 강제 C++ 경로 198개(14.69초), 강제 Python 경로 198개(14.84초) 테스트가 모두 통과했다. 각 실행에 기존 Starlette/httpx 경고 1건이 있었다. API 테스트는 로컬 socketpair 때문에 승인된 샌드박스 외 환경에서 실행했다.

사용·재현
---------

PMA_KEYWORD_BACKEND의 기본값 auto는 호환 확장이 있을 때 C++를 사용하고 없으면 Python으로 동작한다.
python은 Python을 강제하고 cpp는 C++를 강제한다. cpp에서 확장이 없으면 조용히 전환하지 않고 원인을 표시한다.
API 응답이나 DB 스키마는 변경하지 않았다. GPU 가속 모드와 독립적이다.

현재 시제품은 Windows x64 CPython 3.14에서 검증했다. 바이너리는 Git에 포함하지 않고 소스와 빌드 도구를 남겼다.
Zig 실행 파일을 준비한 뒤 새 프로세스에서 빌드·배치하고 앱을 다시 시작한다.

::

    python -m evaluation.build_keyword_native --zig <zig.exe 경로> --install
    python -m evaluation.native_keyword_benchmark --output .local/cpp-bench-new --extension .local/native-keyword/_keyword_native.cp314-win_amd64.pyd

벤치마크는 새 출력 디렉터리만 사용하고 개인 DB를 자동으로 읽지 않는다. 기본 비교 뒤 가장 큰 합성 DB의 교차 실행도 기록한다. 기존 합성 DB만 교차 측정할 때는 --paired-only --db <합성 DB 경로>를 사용한다. Python 기준은 native 자동 선택을 우회하는 python_keyword_matches_batch다.
원시 측정은 .local/native-keyword/comparison, 요약 원시 결과는 evaluation/native_keyword_results.json에 보존했다.
컴파일러 공식 아카이브의 SHA-256을 검증했고 소스·설치 바이너리·빌드 인수의 해시와 버전을 JSON에 기록했다.

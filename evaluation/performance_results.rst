CPU·GPU 성능 측정 및 최적화 결과 — 2026-10-19
==========================================

브랜치: codex/cpu-gpu-performance

요약
----

이번 합성 데이터에서 대부분의 시간은 이미 C++로 실행되는 모델 추론에 사용됐다.
Python 전체를 C++로 이전할 근거는 발견하지 못했다. 명시적 기억 모드의 첫 질문에서
중복 분류를 제거했고, 모델 대기·취소·백그라운드 양보와 추출 재시도 경로를 개선했다.
생성 GPU·임베딩 CPU 조합은 선택 옵션으로 추가했다. 모델, v4 추출 스키마,
추출 문맥·범위, 답변 근거 검증, DB 스키마는 유지했다.

환경과 방법
-----------

* Intel Core i7-13700, RAM 16GB, NVIDIA RTX 3060 8GB. 서버 기본 스레드는 이 PC에서 16개였다.
* Qwen3-8B-Q4_K_M 및 BGE-M3-Q8_0, 생성 문맥 16,384, 임베딩 문맥 8,192 토큰.
* 출력 한도 4,096 토큰, temperature=0, seed=42, top_p=1. 기본 모델 요청 제한 180초,
  대화 전체 제한 300초. 모델 파일 크기·SHA-256은 performance_results.json에 기록했다.
* CPU는 두 서버의 GPU 레이어를 0, GPU 비교는 두 서버를 99로 명시했다.
  GPU가 있는 동일 PC에서 CPU를 강제 실행했다. 물리적으로 GPU가 없는 별도 PC는 미검증이다.
* 개인 DB를 읽거나 수정하지 않았다. 고정 한국어 합성 기록과 별도 SQLite DB만 사용했다.
  같은 실험의 각 반복은 동일한 준비 DB 사본으로 시작했다.
* 기본 비교는 시나리오별 준비 실행 1회 후 5회 측정했다. 모델 시작·초기 준비 시간은
  작업 시간에서 제외했다. 긴 기록은 10문장이며 기존 6문장·600토큰 분할 정책을 사용했다.
* RAM은 Python 작업 프로세스와 두 모델 서버의 작업 집합 합계다. VRAM은 GPU 전체 사용량이다.
  1초 간격 관측 최댓값이며 순간 절대 피크나 시스템 전체 RAM 소비량을 뜻하지 않는다.
  VRAM에는 바탕화면·드라이버 등이 포함되므로 CPU 실행에서도 0이 아니다.
* 일상 사용 PC의 순차 실험이다. 다른 PC·대규모 개인 DB에 대한 성능 보장은 아니다.

CPU의 긴 기록은 180초 읽기 제한을 두 번 넘겨 361.349초 후 실패했다.
같은 실패가 내부 재시도까지 반복되어 나머지 5회 측정은 중단했다.
CPU에서 긴 기록과 대화를 함께 시작한 준비 실행은 대화가 완료됐지만 기록이 실패했다
(전체 410.746초). 이 두 경우는 성공 처리 시간이나 5회 중앙값으로 집계하지 않았다.

GPU의 긴 기록·대화 동시 시작은 5/5 모두 완료됐다. 전체 중앙값은 123.104초,
대화만의 중앙값은 19.914초였다. 이 실험은 준비 단계부터 동시에 시작한 경우이며,
아래의 '이미 추론 중인 요청 뒤에 대기' 검증과 구분한다.

GPU 전체 관측치이므로 메모리 차이를 특정 구성 요소의 정확한 할당량으로 해석하지 않는다.
이를 자동 기본값으로 바꾸지 않고 선택 옵션으로 유지했다.

채택한 변경과 후속 검증
----------------------

* 대화 이력과 주제 맥락이 없는 명시적 기억 모드에서 분류를 다시 호출하지 않는다.
  기억 답변의 실제 생성 서버 HTTP 호출은 기본 비교에서 8회, 후속 실험에서 7회였다.
  자동 모드·후속 대화의 분류와 근거 검증은 유지했다.
* 대화는 기존 5초 대기 제한 대신 전체 요청 시간 안에서 차례를 기다린다.
  대기 중 취소·마감 시간과 백그라운드 양보를 검사한다. 진행 중인 추론을 강제 중단하지 않는다.
* 백그라운드 대기는 모델 HTTP 제한과 분리했다. 추출·임베딩 사이에 대화에 양보한다.
  사실 재구축과 최종 게시도 보호해 답변 중 검색 세대가 불필요하게 바뀌지 않게 했다.
* 임베딩 통신 재시도는 성공한 추출을 재사용한다. 추출 자체의 읽기 시간 초과는
  같은 큰 청크를 자동 반복하지 않는다. 연결 오류 재시도와 기존 청크 복구는 유지했다.
* 내용 없이 단계별 처리 시간과 호출·통신 재시도 횟수를 기록한다.
  겹치는 단계 시간은 합산하지 않는다.

생성 GPU·임베딩 CPU 및 중복 분류 제거를 함께 적용한 5회 후속 실험:

.. list-table:: 선택 혼합 배치 결과
   :header-rows: 1

   * - 작업
     - 중앙값 / 최댓값(초)
     - 기본 GPU 중앙값 대비
   * - 짧은 기록
     - 8.363 / 8.421
     - 약 9.9% 짧음
   * - 기억 답변
     - 12.939 / 13.214
     - 약 15.4% 짧음

모두 성공했다. 두 변경을 함께 적용한 실험이므로 개선 폭을 한 변경에만 귀속하지 않는다.
짧은 기록과 함께 시작한 추가 5회도 대화·기록 모두 완료됐다. 이 경우 대화가 기록 추론보다
먼저 차례를 얻을 수 있으므로 아래의 별도 대기 검증을 수행했다.

추론 시작을 확인한 뒤 대화를 넣은 각 1회 진단에서는 GPU가 8.303초,
CPU가 33.848초 차례를 기다린 후 답변을 완료했다. 대화 시간은 각각 26.222초,
93.820초였으며 두 경우 모두 백그라운드 기록도 저장됐다. CPU 진단의 모델 제한은
아래의 600초 설정을 사용했다. 이 수치를 반복 실험 중앙값으로 해석하지 않는다.

CPU 긴 기록은 제한만 600초로 늘린 별도 1회 진단에서 532.498초에 완료됐다.
원래 추출·검증 경로로 기억 14개가 저장됐다. 파란 책 선물, 지연에게 주지 않았다는 부정,
반납 계획, 캐시 도입 결정, 구현 미시작이 기존 파생 사실 해석에서 유지되는지 확인했다.
이것은 속도 개선이 아니라 완료 가능한 제한 시간의 확인이다. 기본 제한은 180초로 유지했다.

검증 범위에서는 CPU/GPU·혼합 배치의 기억 답변 총 15개가 원문 인용과 모델 검증을 통과하고
기대한 파란 책을 답했다. CPU/GPU 추출 JSON의 세부 필드가 완전히 같다는 보장은 아니며,
이번 확인은 전체 정확도 평가를 대체하지 않는다.

채택하지 않은 실험
------------------

* 8스레드 고정은 오히려 느렸다. 짧은 기록은 51.039 / 51.687초,
  검색은 7.622 / 8.570초였다(각 5/5 성공). 서버가 선택하는 기본값을 유지했다.
  이 PC에서의 관측이며 다른 CPU의 최적 스레드 수를 뜻하지 않는다.
* 문맥을 보존한 문장별 추출은 두 진단에서 출력량을 안정적으로 줄이는 것을 확인하지 못해
  중간에 중단했다. 완료·품질 검증을 마치지 못했으므로 제품 코드에서 철회했고 통계에서 제외했다.
* 벡터 준비·정규화·점수·정렬은 10,000개 × 1,024차원에서 중앙값 57.985ms,
  최댓값 59.041ms였다. 행렬 하나는 약 39.1MiB다. 모델 응답 대비 작아 캐시는 추가하지 않았다.
  이 미세 측정은 큰 DB의 전체 조회·필터 비용을 측정한 것은 아니다.

실행 및 검증
------------

* CPU: ``./run_app.ps1 -Acceleration cpu``
* GPU 자동 선택: ``./run_app.ps1 -Acceleration auto``
* 선택 혼합 배치: ``./run_app.ps1 -Acceleration auto -EmbeddingAcceleration cpu``
* 긴 CPU 기록에 더 긴 시간을 허용할 때만 실행 전 ``$env:PMA_TIMEOUT = '600'``을 설정한다.
  처리 속도는 빨라지지 않는다. 스레드는 미지정 시 서버 기본값을 따른다.
* 외부 서버 모드는 실행 중인 모델 서버 인수를 변경하지 않는다.
* 전체 회귀 테스트 184개 통과. 기존 httpx/Starlette 사용 중단 예정 경고 1개가 남았다.
  새 성능 도구·관련 테스트의 정적 검사와 PowerShell 실행기 검사도 통과했다.
* 모델 서버는 원래 인수로 복구했고 8081·8082 준비 응답을 확인했다.
  변경 코드 적용에는 앱 재시작이 필요하다. 복구 서버까지 정리하려면 기존 stop_app.ps1을 사용한다.

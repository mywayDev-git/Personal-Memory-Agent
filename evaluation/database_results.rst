대량 합성 DB 최적화 측정
=======================

측정일: 2026-10-19. 브랜치: codex/cpu-gpu-performance.

측정 범위
---------

개인 DB를 열지 않고 별도 합성 SQLite DB만 생성했다. 모델 서버는 중단하거나 변경하지 않았다.
CPU·GPU 추론 비교와 별개로, 이번 시간은 DB·필터·벡터·키워드·순위·근거 선택의 로컬 처리 시간이다.
모델 이해·임베딩·선택은 결정적인 대체 구현을 사용했으며 HTTP·실제 추론·답변 생성은 포함하지 않는다.
따라서 아래 비율은 실제 AI 답변 전체 응답 시간의 개선율이 아니다. GPU/VRAM 비교도 이번 범위에 없다.

이전 측정과 같은 i7-13700 / 16GB RAM / RTX 3060 8GB PC에서 수행했다.
각 구현을 새 프로세스로 순차 실행했다. 각 구간은 준비 실행 1회 후 5회 측정했고 중앙값과 최댓값을 기록했다.
OS 파일 캐시를 강제로 비우지 않았다. 구간별 first_seconds는 해당 구간의 준비 실행이며 디스크 콜드 스타트가 아니다.
검색 측정 전에 스냅샷·벡터 구간을 측정하므로 첫 검색도 이미 벡터 캐시가 채워졌을 수 있다.

기억 1천·1만·2만 5천 개, 각각 별도 기록·버전·작업·1024차원 float32 벡터를 생성했다.
기억의 약 1/3에는 근거 2개, 나머지는 1개를 넣었다. 10%는 저장된 대화 기억이며 2.5%는 보관,
2%는 다른 사용자 소유로 설정했다(일부 중복). 범위 필터 후 각각 960·9,600·24,000개가 검색 대상이다.
날짜 필터는 원시 데이터 10%를 지정하며 소유·보관 제외 후 약 6%가 남는다.
이 데이터는 하나의 여행 유형 중심이다. 다양한 문장 길이·관계 분포나 실제 개인 DB를 대표하지 않는다.

채택한 변경
-----------

* 근거 조회: 기억마다 SELECT하던 방식에서 500개 ID 단위 일괄 조회로 변경했다. 같은 읽기 트랜잭션과 position 순서를 유지한다.
* 보관·사용자 제외: 반복 상관 서브쿼리 대신 제외 대상을 한 번 materialize하고 연결한다. 실행 계획의 반복 SCAN c가 사라지고 자동 조인 인덱스를 사용한다. 테이블·영구 인덱스·DB 버전은 바꾸지 않았다.
* 정규화 벡터: 데이터 세대·모델 키·차원·후보 ID 및 순서가 같을 때 단일 행렬을 재사용한다. 다른 부분집합은 교체한다. 배열은 읽기 전용이고 기존 유한값·차원·영벡터 검증을 유지한다.
* 벡터 캐시 예산은 64MiB다. 행렬 바이트와 ID당 128바이트 여유분으로 판정하며 큰 행렬은 저장하지 않는다. 9,600개 행렬은 37.5MiB, 24,000개 행렬은 93.75MiB라 후자는 캐시를 건너뛴다.
* 검색어 정규화: 요청 안에서 같은 단어의 정규화 결과를 최대 16,384개 재사용한다. 보정 검색어에는 별도 캐시를 쓴다. vocabulary에 따른 기존 조사 처리와 원문 위치를 유지한다.
* 전체 스냅샷·JSON 객체를 요청 사이에 보관하는 캐시는 추가하지 않았다. 대규모 데이터에서 RAM을 더 점유하는 것을 피한다.

검색 속도 (초)
--------------

baseline = 수정 전 소스를 보존한 구현. batch = SQL 변경·근거 일괄 조회만 적용.
cached = batch + 벡터 캐시 + 요청 내 검색어 정규화 재사용. 기존 필터·순위·근거 검증은 동일하다.

건수      baseline 중앙/최대    batch 중앙/최대       cached 중앙/최대      시간 감소
----------------------------------------------------------------------------------------
1000      0.090/0.100           0.074/0.081            0.055/0.060           39.3%
10000     1.401/1.457           0.686/0.727            0.515/0.535           63.2%
25000     5.801/5.912           1.797/1.827            1.456/1.494           74.9%

스냅샷 / 벡터 준비·점수·정렬 / 날짜 필터 검색: 중앙값 (초)

건수      스냅샷 전→후        벡터 전→후          날짜 검색 전→후
-----------------------------------------------------------------------------
1000      0.0432→0.0270           0.0045→0.0002           0.0535→0.0366
10000     1.0156→0.3115           0.0440→0.0021           1.0555→0.3539
25000     4.9072→0.9388           0.1108→0.1157           4.9557→0.9040

스냅샷 SQL 수(세대 확인 포함)는 962→4, 9,602→22, 24,002→50으로 감소했다.
행렬 캐시가 없는 2만 5천 건에서도 SQL과 검색어 재사용만으로 개선됐다.

RAM 비교 (MiB)
--------------

아래는 각 프로세스의 전체 후보 검색 5회 후 working set과 그 시점까지의 최고 working set이다.
프로세스에는 앞선 스냅샷·벡터 분리 측정도 포함되므로 최고값을 단일 실제 API 요청의 메모리라고 해석하면 안 된다.
모델 서버 메모리는 제외했다. RSS는 파이썬 할당자·GC·OS 회수의 영향도 받는다.

건수       전 RSS / 최고         후 RSS / 최고
--------------------------------------------------------------
1000       69.7 / 88.2            71.9 / 85.8
10000      104.3 / 334.0            139.2 / 334.2
25000      127.3 / 748.4            117.8 / 748.9

1만 건은 행렬 유지로 상주 RAM이 약 35MiB 증가한다. 캐시 한도는 이 비용을 제한하기 위한 선택이다.
2만 5천 건은 전체 행렬을 보관하지 않는다. 이 경우 관측된 RSS 감소를 모든 환경에서 보장하는 메모리 절감으로 해석하지 않는다.

남은 병목과 C++ 검토
--------------------

추가로 2만 5천 건 전체 검색만 수행하는 별도 프로세스를 실행했다. 준비 1회 + 5회이며 기존 단계 경계에 경량 타이머를 붙였다.
이 측정의 중앙값은 수정 전 5.740초, 수정 후 1.514초다. 위 표와는 별도 측정이다.
cProfile 수치는 호출 추적 오버헤드가 있으므로 실행시간 표와 직접 더하거나 비교하지 않았다. 원시 JSON에 상위 함수 비용을 보존했다.

단계                    이전 중앙값       이후 중앙값 (초)
-----------------------------------------------------------------
snapshot                  4.5528             0.6356
structure_filter          0.1700             0.1664
vector_retrieval          0.1300             0.1302
keyword_retrieval         0.8084             0.4743
rank_fusion               0.0249             0.0231
source_validation         0.0682             0.0680
relation_lookup           0.0027             0.0026

단계별 중앙값은 서로 다른 실행의 중앙값일 수 있어 합계와 정확히 같지 않다.
수정 후 DB 읽기·JSON 변환과 검색어 매칭이 남았다. SQLite·NumPy 및 JSON 디코더의 네이티브 작업은 Python 호출부를 C++로 바꾸는 것만으로 제거되지 않는다.
부분 C++ 후보는 keyword_matches의 배치 토큰 매칭이다. 이 단계 0.474초를 완전히 없앤다는 비현실적인 가정에서도 전체 단축 상한은 약 31.3%다.
실제 C++ 구현은 데이터 전달·Unicode casefold·토큰화·vocabulary 기반 조사 처리·Python 문자 오프셋·결과 객체 생성 비용을 포함하므로 이 상한보다 작다.
C++ 시제품이나 실제 C++ 속도 비교는 수행하지 않았다. 이 수치는 이론적인 범위 검토이며 네이티브 개선율이 아니다.
이번 채택 판단: 측정상 개선이 확인된 SQL·일괄 조회·캐시를 유지하고 C++ 확장은 추가하지 않는다.
향후 더 큰 데이터에서 부분 C++를 시도한다면 검색어 매칭 전체를 한 번의 호출로 넘기는 범위로 제한하고, 현재와 같은 결과·순위·부정 표현·Unicode 위치를 비교해야 한다.
DB 전체 재작성은 현재 측정에서 추가 효과를 입증하지 못했다.

검증·재현
---------

* 세 규모 × 세 구현의 스냅샷 전체, 벡터 top-k, 전체 검색 응답, 날짜 필터 검색 응답의 SHA-256이 각각 일치했다. 응답에는 근거·순위·검색 설명이 포함된다.
* 별도 단계 측정의 전체 응답도 일치했다.
* 일괄 조회의 배치 경계·근거 순서·수정 격리, 보관/소유자/없는 버전, 빈 DB·다른 모델, 수정·삭제 후 검색, 세대·모델·부분집합·순서 변경과 예산 초과를 테스트했다.
* 기존 근거 검증·취소·타임아웃·대화 테스트를 포함해 전체 190개 테스트가 통과했다(15.01초). 기존 Starlette/httpx 사용 중단 경고 1건이 있었다. 린트와 diff 공백 검사도 통과했다.
* 샌드박스에서 API 테스트가 socketpair 생성에 멈추는 환경 제약을 확인해 전체 테스트는 승인된 샌드박스 외 실행으로 검증했다. 제품 코드를 바꿔 우회하지 않았다.
* 최초 탐색 run1은 구현 변경 도중 측정되어 최종 통계에서 제외했다. smoke/reference-check도 최종 성능 수치에 합산하지 않았다.

재현 명령 (새 출력 디렉터리 필요):

::

    python -m evaluation.database_benchmark --output .local/db-bench-new --sizes 1000 10000 25000 --samples 5

기본값은 evaluation/database_reference.py의 이전 알고리즘이다. 이번 원본 측정은 --baseline .local/db-performance/final의 수정 전 전체 소스를 사용했다.
이후 구현의 파일과 해시는 manifest에 보존했다. .local/db-performance/final에는 합성 DB·이전/이후 소스·원시 측정이 있다.
저장소에 남기는 요약 원시 결과는 evaluation/database_results.json이다.

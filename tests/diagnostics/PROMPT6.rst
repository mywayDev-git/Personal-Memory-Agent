모델 근거 선정·생성·검증 계측 — Prompt 6
=======================================

2026-10-17 (Asia/Seoul), codex/search-diagnostics-v1.

완료 범위
---------

* evidence_selection_batch: 실제 4개 이하 배치마다 입력 가명 ID, 선정·미선정,
  반환 순서의 model_selected_refs, 입출력 개수, 배치 번호(0부터), 시간과 오류.
* evidence_selection_merge: 배치별 반환을 이어 붙인 순서와 앞 8개 반환 결과,
  evidence_limit로 잘린 ID. 중복은 원래처럼 유지하며 후보 순번으로 구분한다.
* model_understanding: 모델 호출, JSON 파싱, 스키마 검사, 시간·인물 조건 유무.
* model_answer: 입력 근거, 출력 인용 가명 ID, 생성 성공·오류, feedback 재생성 여부.
* model_review/model_verify: 검증 결과·오류·호출 여부. 서비스의 최종 판단과
  구분되는 모델 경계 이벤트이며 서비스 단계 이벤트 수를 늘리지 않는다.
* 서비스 요약도 모델 내부 개수 제한을 evidence_limit로 표시한다.

pma/models.py에는 데코레이터와 기존 통신·파싱 경계의 관찰 호출만 추가했다.
프롬프트, 모델 옵션, 스키마, 생성 토큰 수, 4개 배치, 8개 반환 제한,
정렬·선정 알고리즘 및 기존 예외 처리는 그대로이다. 별도 모델 호출은 없다.
pma/model_diagnostics.py는 요청 ContextVar를 사용하고 관찰 실패를 격리한다.
원문 질문·응답·검증 사유·오류 메시지를 기록하지 않는다. 기본 진단 OFF 유지.

검증
----

먼저 보완한 모델 계약에서 11 failed, 1 passed를 확인한 뒤 구현했다.
최종 모델 계약 27개 및 전체 454개 통과, 기존 Starlette 경고 1개, 21.49초.
전체 결과: .local/diagnostics-prompt6.xml. Ruff 및 git diff --check 통과.

선정 입력 0/1/4/5/10개, 빈 선정, 중복·없는 ID, 실제 JSON 파싱·스키마 실패,
네트워크 오류, 예외 객체 보존, 계측 실패, 최종 제한, 서비스 요약 연결을 검증했다.
진단 ON/OFF의 통신 직전 payload·스키마·옵션·호출 횟수와 결과를 비교했다.
기존·실험 답변 정책 모두 생성/재생성/검증 요청의 불변성을 확인했다.
변경 diff에서도 기존 프롬프트 및 옵션 문자열이 수정되지 않았음을 확인했다.

관찰 한계와 다음 단계
-------------------

model_called는 실제 chat 진입 경계에서 표시한다. structured를 대체한 테스트나
외부 구현은 실제 호출·파싱 여부를 관찰할 수 없어 파싱 필드를 만들지 않는다.

빈 선정 입력은 모델을 호출하지 않으므로 배치 이벤트도 없다.
시간은 해당 메서드 전체 시간으로 순수 서버 추론 지연이 아니다.
실제 LLM 서버 E2E는 실행하지 않았다.

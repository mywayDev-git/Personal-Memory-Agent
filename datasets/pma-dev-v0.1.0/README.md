# Personal Memory Agent 개발 테스트셋 v0.1.0

원문과 질문을 분리하고, 질문에 예상 답변과 판정 기준을 붙인 합성 개발용 데이터셋이다. `REVIEW.md`에서 원문·질문·예상 답변을 함께 읽을 수 있다. 모델을 실행하거나 기존 앱의 예시 결과를 실제 결과로 바꾸지 않는다.

**현재 상태: 작성자 초안 / 의미 정답은 사용자 검토 전 / 실제 모델 평가 미실행.** 데이터 연결과 원문 위치의 정적 검증 통과는 모델 정확도나 제품 기능 통과가 아니다.

현재 구성은 **36개 계열 · 원문 59개 · 기억 상태 55개 · 질문 114개 · 의미 사실 96개 · 원문 간 관계 11개**다. 원문 27개는 기존 개발용 원문을 그대로 재사용했고, 32개는 새로 작성했다. 원본 489개 변수 중 155개에 초안 계열을 연결했으며 334개는 아직 작성하지 않았다. 연결된 155개도 변수 전체 조건의 검증 완료를 의미하지 않는다.

## 계획 점검 결과

1. 하나의 버전 고정 데이터셋으로 후보를 비교한다. 다만 모든 원문을 하나의 기억 DB에 섞지 않고 `context_id`마다 별도 합성 저장소를 만든다.
2. 원문 구조화는 특정 질문에 필요한 정보만 평가하지 않는다. `sources.json`의 질문 독립적인 의미 사실과 근거를 먼저 확인한다. 현재 원문 정답은 명시한 사실 범위의 초안이며, 원문의 모든 가능한 구조화를 완전히 열거했다는 뜻은 아니다.
3. 사건·개체·관계 방식에 특정 JSON 모양을 강제하지 않는다. 의미 보존·주체·부정·조건·시간·근거로 비교하고, 각 방식이 표현하지 못하는 내용도 보고한다. 이 파일의 `facts`는 평가용 의미 단위이지, 제품이 출력해야 할 triples 스키마가 아니다.
4. 질문 정답은 대표 문장 하나와 문자열 일치로 판정하지 않는다. 필수 주장, 금지 주장, 응답 행동, 필요한 근거 그룹을 함께 확인한다. 부정문 안에서 금지 값을 설명했다고 무조건 실패시키지 않는다.
5. 원문 표현 변경 / 의미 값 변경 / 방해 기록 추가 / 기록 순서 변경 / 수정·삭제 상태 변경을 구별한다. 한 번에 여러 축을 바꾼 결과는 조합 탐색이지 특정 축의 효과로 해석하지 않는다.
6. 모델, 구조화 방식·버전, 단계별 프롬프트, 검색 설정은 데이터 파일 밖의 실행 설정에 둔다. 데이터·정답을 후보마다 맞춰 바꾸지 않는다.
7. 구조화 → 고정한 구조화 산출물로 검색 → 고정한 검색 결과로 답변 → 전체 경로 검증 순서로 진행한다. 실제 관측이 없는 검색 점수·지연·보안 판정은 만들지 않는다.
8. 개발용 데이터를 읽고 튜닝한 뒤 이것을 최종 미공개 평가셋으로 재명명하지 않는다. 원본 저장소의 final 데이터는 가져오지 않았다. 이 초안에는 final 분할이 없으며, 최종 평가 전 별도 계열을 확보해야 한다.

## 파일 구성

| 파일 | 책임 |
|---|---|
| `sources.json` | 원문, 시스템 메타데이터, 보존할 의미 사실, 정확한 원문 구간, 역할 하이라이트, 원문 간 관계 |
| `questions.json` | 질문, context 연결, 대표 답변, 필수·금지 주장, 응답 행동, 근거 그룹 |
| `contexts.json` | 처음 저장할 원문, 실행 순서, 현재 시각, 사용자, 대화 맥락, 변경 후 상태, 필요한 관측 |
| `coverage.json` | 기존 489개 변수의 설명과 이번 초안 연결; 미작성 항목도 보존 |
| `manifest.json` | 버전, 계열, 파일 해시, 원본 파일 출처·해시, 비교 계약 |
| `REVIEW.md` | 사람이 원문과 예상 답변을 함께 읽는 검토 문서 |
| `review-log.json` | 실제 사람의 정답 검토 기록을 남길 빈 양식; 승인 내역 없음 |
| `validate.mjs` / `lib.mjs` | 로컬 데이터 무결성 검사와 상태 준비 로직; 모델 호출 없음 |
| `prepare.mjs` | 모델 입력과 비공개 정답을 분리한 실행 준비 스냅샷 생성; 평가 실행 없음 |
| `config.example.json` | 후보 설정의 자리만 보여 주는 예시; 모델·프롬프트 미선택 |
| `validation-report.json` | 정적 검증 결과; 모델 성적표가 아님 |

기존 개발용 원문 일부를 그대로 재사용하고 새 합성 원문과 질문을 추가했다. 재사용 원문은 `provenance.source_id`로 원본을 추적한다. 저장 시각은 별도 설계한 합성 메타데이터이며 원본의 실제 저장 이력을 의미하지 않는다. 원본 파일은 변경하지 않았다.

## 질문과 근거의 계약

`question.context_id`가 테스트의 기억 범위를 결정한다. 같은 질문을 다른 상태에서 물으면 각각 독립된 검사 조건이다. 동일 문장 질문을 화면에서 묶어 보여 주어도 context가 다른 행을 합쳐 없애지 않는다.

`gold.evidence_groups`는 **그룹 사이는 모두 필요(AND), 그룹 안의 사실은 대안(OR)**이다. F12-Q3은 변경 전·후 양쪽이 필요하고, F32-Q1은 같은 사건을 설명하는 두 출처 중 하나로 충분하다. F32-Q3은 두 출처를 요청하므로 양쪽 그룹이 필요하다.

`gold.required_claims`는 의미 판정 항목이다. 예를 들어 “0.92는 PMB의 값이므로 PMA 값으로 쓸 수 없다”는 답변을 `0.92`라는 단어가 있다는 이유만으로 실패시키지 않는다. 대표 답변을 복사해야만 정답인 것도 아니다. 응답 행동은 `answer`, `partial_answer`, `abstain`, `clarify`, `report_conflict`, `deny`로 구분한다.

원문 위치는 **UTF-16 코드 유닛, 0부터 시작, 끝 미포함**이다. `text.slice(start,end) === quote`가 성립해야 한다. Python 코드 포인트 위치와 혼용하지 않는다. 이모지가 포함된 F21은 이를 확인하는 사례다. 원문을 NFC 변환하거나 줄바꿈을 바꾸면 원문 버전과 위치도 다시 작성해야 한다.

원문 ID와 revision은 불변 스냅샷을 식별한다. F27의 V1/V2는 서로 다른 원문 스냅샷이며, `replace` 단계가 같은 논리 기록 `record-27`의 교체임을 지정한다. 현재 검색에서는 교체된 V1을 제외한다. F16의 RAM 96→48 대조는 시간상 갱신이 아니라 별도 실험 입력이다.

원문 간 관계 방향은 `from_source_id → to_source_id`다. 예를 들어 `superseded_by`는 앞 원문이 뒤 원문으로 대체됨을 뜻한다. 같은 단어가 나온다는 이유만으로 관계를 정답으로 등록하지 않는다.

## 단계와 관측

`contexts.setup.steps`는 순서대로 실행해야 하는 신뢰된 테스트 하네스의 명세다. 아직 제품 실행 어댑터는 연결하지 않았다. `lib.mjs`의 상태 준비는 명세 일관성 검사이며 실제 저장·삭제·캐시 무효화를 실행했다는 증거가 아니다.

F28-DELETED는 먼저 질문해 캐시를 만들고 삭제하는 순서를 포함한다. F29는 비저장 발화 후 새 세션을 연다. F30은 다른 사용자 원문이 저장소에 있더라도 검색 후보 단계에서 차단되는지 관측해야 한다. 답변에 비밀 값이 안 나왔다는 이유만으로 권한 필터 통과를 판정할 수 없다.

F26과 F33의 이전 답변·검색 결과는 `fixed_test_fixture`로 제공하는 통제된 맥락이다. 이 조건은 **고정된 정상 맥락에서 후속 질문을 이해하는지**를 검사한다. 실제 첫 답변 오류가 다음 턴에 미치는 영향까지 평가하려면 앞 턴을 실제로 실행하는 별도 연속 대화 경로가 필요하다. 고정 답변을 실제 모델의 과거 응답으로 표시하지 않는다.

시스템의 owner/저장 시각/동의 정책은 신뢰된 입력이다. LLM이 추측해서 생성하는 정답 필드가 아니다. 상대 시간은 원문 기록 시각과 시간대를 기준으로 해석하고, 현재 상태 질문은 context의 `now`를 사용한다. 예정일 경과만으로 완료를 추론하지 않는다.

## 로컬에서 데이터 확인

이 폴더에서 다음 명령은 모델·임베딩·DB 서버 없이 동작한다.

```powershell
node validate.mjs
node prepare.mjs --out .\prepared-input-preview --config .\config.example.json
```

입력 준비기는 새 출력 폴더만 허용한다. 같은 경로를 다시 쓰려면 다른 출력 폴더 이름을 지정한다. `run-plan.json`에 데이터와 설정의 해시 및 `NOT_RUN`을 남긴다.

준비 결과 중 `model-extraction-inputs.json`은 해당 사용자에게 허용된 현재 원문만 포함한다. `question-inputs.json`은 질문·대화 맥락·검색 범위이며, 답변 모델에는 별도로 **실제 검색한** 근거를 넘겨야 한다. 정답 근거를 대신 넘기면 검색 성능 평가가 아니다.

`system-fixture.json`은 다른 사용자 원문과 삭제 전 원문을 포함하는 신뢰된 하네스 전용 입력이다. LLM에 통째로 넣지 않는다. `evaluation-private.json`, `sources.gold`, 정답 관계, 예상 상태는 모델 프롬프트에 넣지 않는다. 같은 폴더에 분리해 둔 것만으로 접근 보안이 강제되는 것은 아니며 실제 실행기에서 입력 허용 목록을 적용해야 한다.

스냅샷 구조화 입력은 변경 이후 상태의 모델 비교에는 쓸 수 있지만 삭제·동의·권한 시스템의 실제 구현 검증을 대신하지 않는다. 현재 데이터 준비기는 모델을 다운로드·선택·호출하지 않으며 기존 UI나 공식 평가기에 자동 연결하지 않는다.

## 다음 보완과 판정

먼저 F02(역할), F06(조건), F10(시간), F12(변경), F21(장문), F28(삭제), F30(권한)의 원문·질문·정답을 사람이 검토해 기준을 맞춘다. 승인 내역은 ID, 검토 대상 해시, 승인/수정 필요, 검토자, 일시와 이유로 남긴다. 정답을 고치면 데이터 버전과 manifest 해시도 갱신한다.

현재 변수 연결은 계열 수준의 **작성 초안**이다. 489개 전체 검증 완료가 아니다. UI 조작·접근성·파일 가져오기·성능 부하·장애·실제 동시성·일부 생명주기는 별도 실행 명세와 어댑터가 필요하다. `coverage.json`에서 비어 있는 항목을 확장하고, 연결된 변수도 원 명세의 세부 조건을 전부 대조해야 한다.

이번 버전은 핵심 의미 조건과 몇 가지 상태 변화의 출발점이다. 모든 변수의 전수 조합, pairwise 조합, 매우 긴 문서·실제 파일 가져오기, 실제 모델 비결정성은 아직 준비하지 않았다. 특히 F21은 자연스러운 복합 서사이지 문맥 길이 한계나 대용량 성능 검사가 아니다. 다음 확장에서는 위험도가 높은 부정×동명이인×정정, 시간×권한×삭제 같은 조합을 추가하고 각 변경에서 무엇을 고정했는지 명시해야 한다.

어떤 후보도 이 단계에서 합격/불합격이나 추천 모델로 결정하지 않는다. 실제 실행 후에는 구조화 의미 보존, 근거 검색, 근거 기반 답변, 시스템 동작을 별도로 보고하고 미실행·오류·검토 대기를 분모에서 숨기지 않는다.

인용·답변 완결성 보완 실험
=========================

기존 두 실패의 보완은 확인했지만 전체 품질 조건은 미통과다. 속도 최적화와 CPU·GPU
성능 재비교는 시작하지 않았다. 빠른 오답이나 정상 답변 거절을 개선으로 채택하지 않는다.

자료 고정과 실행 조건
--------------------

* 출발점: ``codex/first-response-cpu-gpu``의 ``8e4deea``.
* 제품 변경 전 ``cf99499``에서 새 합성 32개를 개발 16개·독립 확인 16개로 고정했다.
* 원문·질문·허용 답변·금지 인용·정상/변조 답변 쌍의 SHA256은
  ``9a04e341f3beaaf319e6ee5eb61b9b96be844e796f73a7063b0dd46995e70c25``다.
* 기존 ``complete_unknown_attribute``와 ``complete_unknown_followup``은 노출된 회귀 사례다.
  새 독립 사례로 다시 계산하지 않는다. 최종 확인 자료는 개발용 수정에 쓰지 않는다.
* Qwen3-8B Q4_K_M·BGE-M3 Q8_0을 유지한다. 개인 DB·공식 메인 평가는 사용하지 않는다.
* 독립 확인 문장은 사람이 작성한 합성 자료다. 일부 이름 뒤 조사가 어색한 문장도 동결 후
  고치지 않고 보존한다. 이 작은 자료 집합의 통과가 모든 표현의 정확성 보장은 아니다.
* 최초 확인 세트 중 계획·실행과 지시문 사례는 개발 세트와 질문·원문이 중복이었다.
  이를 완전 독립 16개로 보고하지 않는다. 원래 16개 결과는 보존하고 두 공통 통제 사례도
  계속 채택 조건에 포함한다. 확인 세트의 다른 14개는 개발 원문과 질문이 다르다.
* ``df4d6f5``에서 별도 원문 2개를 추가로 고정했다. SHA256은
  ``7bfb6ba409dba08bb9dec200b67efe560183f4cccc55676c1d3b7b2e82e5fb83``다.
  이는 최초 제품 수정 후에 고정한 보충 확인 자료이며, 최초 32개 동결과 구별한다.
  보충 자료 고정 후 제품을 다시 조정하지 않는다. 원래 실패를 새 사례로 대체해 숨기지 않는다.

제품 보완
---------

* 선택된 인물의 직업 질문에 다른 사람이나 인물이 전혀 없는 기록을 인용하면 거부한다.
* 키만 답하는 응답과 별도 원문에 직업이 있는데도 미상이라고만 답하는 응답을 거부한다.
* 직업 미기록과 실제 무직을 구별한다. 좁은 다른 속성 전용 기록의 한계 설명 후보도 항상 새
  독립 검증을 통과해야 하며, 전체 DB에 직업이 없다고 단정하지 않는다.
* 검증 모델은 원문 전체를 읽되 답변이 인용하지 않은 기록을 승인 근거로 추가할 수 없다.
  형식·인용·주장 검사를 통과하지 못하면 기존 재생성·재검증 후 근거 부족 경로를 쓴다.
* 별도 직업 원문이 선택 단계에서 빠졌어도 현재 요청에 확보된 전체 관련 원문으로 미상
  답변을 점검한다. 이는 DB 전체에 대한 부재 증명이 아니다.
* 실측에서 효과가 없었던 지시문 선택지·추가 지침·중복 표현 변경은 ``b120198``에서
  적용 코드에서 제외했다. 그 시제품의 테스트와 결과만으로 채택을 주장하지 않는다.
* API 응답·DB 스키마·기본 모델은 유지한다. 기본 프로젝트 체크아웃은 바꾸지 않는다.

개발 중 발견한 실패도 보존
------------------------

* ``integrity-development-v1``: 새 자료 인자 연결이 빠져 모델 추론 전에 실패했다.
  일반 서버 정리·복구 기록을 보존했다.
* ``integrity-development-v2``: 모자 메모를 인물의 직업 미상의 근거로 승인해 중단했다.
* ``integrity-development-v3``: 정상 4개 승인·변조 4개 거부였지만 검증 형식 오류 1개가
  있어 통과로 표시하지 않고 중단했다.
* ``integrity-development-v4``: 답변 쌍 8/8, 질문 15/16. 지시문 색을 실제 선택지로
  제시한 명확화 실패 때문에 미채택이다. 검증된 앞선 대화만 후속 개발 재검사에 공유한다.
* ``integrity-development-v5``: 답변 쌍 8/8, 질문 15/16. 지시문 선택지를 배제해도
  독립 검증이 올바른 흰색 답변을 거부했다. 이것도 통과로 계산하지 않는다.
* ``integrity-instruction-diagnostic``, ``integrity-instruction-policy-check``,
  ``integrity-instruction-single-copy``: 지시문 사례만 각각 재현했다. 추가 지침과 원문을
  보존한 중복 제거도 오거절을 해소하지 못했다. 모두 미채택이며 원래 자료를 유지했다.

고정 확인 결과와 남은 오류
-------------------------

* 새 확인 세트는 **14/16**이었다. 정상·변조 답변 쌍은 정상 4개 승인·변조 4개 거부,
  형식 오류 0개였다. 개발에서 이미 본 통제 사례 2개는 별도로 표시한다.
* ``confirmation_ambiguous``: 두 역할의 유진이 있는 자료에서 이름만 물었지만
  ``유진의 직업은 제과사입니다.``라고 확정하고 독립 검증을 통과했다. 인용문 자체는
  합창단 친구에 대해 맞지만 질문이 어느 유진인지 구분되지 않았다. 최종 근거 묶음에는
  병원 동료 유진이 없었다. **모호한 인물의 잘못된 확정 승인 1건**으로 실패를 유지한다.
  원래 자동 채점의 인용 범위 통과만으로 이 의미 오류를 숨기지 않는다.
* ``confirmation_injection``: 실제 흰색 모자와 지시문 속 검은색 모자를 선택지로 제시했다.
  사실 질문에 불필요하게 되물어 정상 답변에 실패했다. 이 사례는 개발과 중복된 통제다.
* 실패한 최종 확인 답변에 맞춰 제품·정답·임계값을 다시 바꾸지 않았다. 향후 수정에서는
  이 자료를 회귀용으로 전환하고 새로운 독립 확인 자료를 먼저 고정해야 한다.
* 자동 비교 표시는 기준이 없는 후보 단독 실행이어도 절대 품질 실패면
  ``NOT_ELIGIBLE_ABSOLUTE_QUALITY``가 되도록 했다. 기준 부재를 품질 통과로 취급하지 않는다.
* 보충 확인은 **1/2**였다. 다른 원문의 계획·실행 구분은 통과했지만 갈색 장화와 지시문 속
  분홍색 장화를 되물었다. 개발과 다른 원문·질문의 최초 확인 14개 중 13개와 보충 2개 중
  1개를 합쳐, **중복 없는 새 입력 16개 기준도 14/16**이다. 이 두 집계는 14개를 공유하므로
  서로 독립된 32회 확인으로 더하지 않는다. 원래 공통 통제의 실패도 계속 미통과 조건이다.

기존 두 실패의 최종 코드 재확인
------------------------------

제품에 남긴 ``b120198``의 보완 코드로 기존 두 질문 모두 실제 GPU에서 통과했다.
두 답변은 ``독서 모임 친구 서윤의 직업은 현재 확인한 기록만으로는 알 수 없습니다.``였고,
인용은 ``독서 모임 친구 서윤은 키가 172cm다.``만 사용했다. 연구실 동료 현우나 다른 역할의
서윤은 인용하지 않았다. 독립 모델 검증은 별도 호출로 유지했다.

============================= =============== ============ ===========
사례                          현재 요청(초)   Qwen 호출    BGE 호출
============================= =============== ============ ===========
명시적 역할의 직업 미기록       43.697          12           2
같은 인물의 후속 직업 질문     47.724          12           2
============================= =============== ============ ===========

각각 품질 확인 1회이며 준비 실행 후 5회 중앙값이 아니다. 앞선 대화는 이전에 검증한 합성
대화를 가져왔다. 대상 GPU가 이번 실행에서 그 대화를 직접 준비한 것으로 표시하지 않는다.
요청·내부 통신 실패는 이 두 요청에서 0건이었다. 호출 수에는 최종 독립 검증·재생성을 포함한다.

이 두 요청의 평가 프로세스·모델 서버 RAM 합의 피크는 각각 6814·5578 MiB,
private commit은 9927·9931 MiB, 다른 앱을 포함한 장치 VRAM은 둘 다 7773 MiB였다.
단일 품질 실행의 관측값이며 이전 실패 답변이나 다른 CPU 입력과 메모리 개선율을 계산하지 않는다.

성능 비교 중단 조건
------------------

전체 품질 실패 때문에 CPU 비교, 준비 실행 후 기준·후보 각 5회, GPU 최종 후보 20회,
입력 압축·캐시 최적화는 진행하지 않았다. GPU의 단일 품질 확인 시간·메모리는 원시 결과에
남지만 속도 개선율이나 안정성·메모리 증가 5% 조건의 통과 근거가 아니다.
이전 CPU·GPU 결과를 이번 수정의 재측정 결과로 재사용하지 않는다.

확인·재현 방법
--------------

모델을 구동하지 않고 고정 자료 계획만 확인한다::

    & C:\development\Personal-Memory-Agent\.venv\Scripts\python.exe -m evaluation.first_response --split integrity_confirmation

작업 폴더에서 아래 명령은 실행 계획만 표시한다. 실제 실행에는 ``-Execute``를 추가한다::

    ./scripts/run_latency_goal.ps1 -Placement gpu -QualityScreen -CandidateOnly -ReviewBank -IntermediatePlanning -BoundedExpansions -SourceDateDrafts -ContextShortcut -ColdInterpretations -FixtureSplit integrity_confirmation -GenerationBatchThreads 24 -PythonExe C:/development/Personal-Memory-Agent/.venv/Scripts/python.exe -PauseOrdinaryModels -RunName my-integrity-confirmation

매번 새로운 ``RunName``을 사용한다. 결과 폴더의 ``answers.html``은 저장된 질문·답변·
정확한 인용·원문을 읽는 표다. 열거나 새로고침해도 모델을 실행하지 않는다.
``review-quality.json``에서 정상·변조 답변의 실제 독립 검증 결과도 확인한다.
``-AnchorTemplates``로 공유한 대화는 대상 장치가 그 대화를 직접 준비했다는 뜻이 아니다.

최종 자료
---------

* ``.local/latency-goal/integrity-independent-confirmation``: 원래 확인 세트 14/16과 답변 쌍 8/8.
* ``.local/latency-goal/integrity-source-disjoint-supplement``: 별도 고정한 두 원문의 추가 확인.
* ``.local/latency-goal/integrity-retained-original-two``: 남긴 코드에서 기존 두 실패의 재확인.
* ``docs/answer_integrity_results.json``: 점수·실패·시간·호출·메모리·해시와 독립 범위 구분.

오프라인 검사는 **1033개 통과**, 기존 Starlette 사용 중단 예고 1개였다.
마지막 모델 실행 후 8081·8082 서버의 원래 실행 설정과 health 200을 확인했다.
소유 실험 서버는 0개였다. 개인 DB·다른 앱·앱 기본 모델·기본 체크아웃은 유지했다.
작업 폴더 ``.local`` 전체 약 17.24 GiB, 남은 공간 약 17.89 GiB로 디스크 제한 안이었다.

원문 대조 결과는 각 원시 실행 폴더의 ``source-adjudication.json``에도 보존했다.
이는 에이전트 검토이며 사용자 검토를 대신하지 않는다. 원래 자동 점수는 변경하지 않았다.
최종 모델 실행 중 제품·평가 소스가 바뀌지 않은 것은 실행별 해시로 확인했다.
이번 결과는 기존 두 재현 오류의 보완이며 전체 품질 통과·기본 프로필 채택·목표 속도 달성은 아니다.

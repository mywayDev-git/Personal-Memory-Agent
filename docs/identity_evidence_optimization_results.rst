동명이인 근거 보존·과도한 거절 수정과 CPU/GPU 재비교
=====================================================

작업 및 범위
------------

작업 브랜치는 ``codex/first-response-cpu-gpu``이며 제품 비교 코드는 ``4a41f8f``입니다.
기본 프로젝트의 ``codex/response-latency-recheck``와 ``8cb40f5``는 변경하지 않았습니다.
Qwen3-8B Q4_K_M·BGE-M3 Q8_0과 최종 독립 검증을 유지했습니다.
개인 DB, 공식 메인 평가, 모델 다운로드, 다른 앱 종료, 기본 모델 교체,
기본 브랜치 병합·푸시는 수행하지 않았습니다.

품질 수정
---------

* 기존 필터를 통과한 동명이인 역할 근거가 모델 선별이나 후보 상한에서 빠지지 않도록
  보존합니다. 삭제·소유자·버전·날짜 필터에서 제외된 기록은 되살리지 않습니다.
* 직업 질문에서 해당 인물의 키 기록을 잃거나, 별도 기록의 직업보다 뒤로 밀려
  잘못 근거 부족으로 처리되는 문제를 보완했습니다.
* 병원 근무자의 단일 직업 문장이 환자 건강정보로 잘못 분류되는 경우를 수정했습니다.
  실제 진료·진단 정보 및 민감정보가 덧붙은 원문의 기존 제한은 유지합니다.
* 이유를 답한 뒤 덧붙인 정상 사실과, 이유 없이 사건만 반복한 미완료 답변을 구별합니다.
  직업·이유 미상이라는 적절한 한계 설명은 허용하며 미기록을 실제 부재로 단정하지 않습니다.
* 원문 속 명령이 섞인 경우 실제 사실의 인용을 먼저 선택해 검증합니다. 명령 내부를
  부분 인용하거나 다른 사람·다른 물건의 인용으로 승인한 결과는 서버에서 거부합니다.
  최종 독립 검증 호출, 원문 확인, 재생성·재검증·근거 부족 복귀는 유지합니다.

먼저 고정한 독립 자료
--------------------

v2 독립 확인에서는 정상 구입 사실의 과도한 거절 1건이 남아 후보를 탈락시켰습니다.
그 자료를 회귀용으로 전환한 뒤 ``03a95f4``에서 v3 개발/확인 원문을 새로 고정했습니다.
v3 자료 SHA256은 ``ad4216b6996f3518b05b716936678f7f56299f643b271bd7dc0d59fbe126a934``입니다.
품질 수정 뒤 실제 GPU 확인 16/16, 정상·변조 답변 검증 16/16,
기존 회귀 16/16·검증 8/8을 통과했습니다. CPU 검증 전용 확인도 16/16입니다.

추가 인용 경계 자료는 수정 전 ``c286f50``에서 개발 4개·확인 4개를 고정했습니다.
SHA256은 ``51c43ed8d427e0230c80b1951228cd7827d5457d29b829a9e8a9390dff887384``입니다.
의도적으로 잘못 승인하는 검증기를 흉내 낸 오프라인 비교에서
잘못 승인 3→0건, 잘못된 인용 위치 2→0건, 정상 답변 거절 0→0건입니다.
이는 실제 모델 오류율 측정과 구별합니다.

새 단일 원문 최적화 전 ``7b6b30b``에서 개발 16개·독립 확인 16개,
각 정상/변조 답변 8쌍을 고정했습니다. 인물·상황과 원문은 이전 자료 및 두 분할 사이에
겹치지 않으며, 같은 유형의 합성 사례라는 한계는 있습니다.
SHA256은 ``c2cb2c7ff162ea36d07d1cb0f742c478b7b910266c33d48fead5bd5a3ef8554e``입니다.

``4a41f8f`` 실제 GPU 개발은 질문 16/16·검증 16/16,
처음 실행한 독립 확인도 질문 16/16·검증 16/16을 통과했습니다.
답변과 선택 인용을 합성 원문에 직접 대조해 중요한 오답 승인·다른 사람 인용·
정상 답변의 과도한 거절을 관측하지 않았습니다. 부정 취소 답변의 같은 사실 반복은
표현상의 잔여 문제로 기록했습니다. 모델 승인 자체를 정답으로 삼지 않았습니다.
전체 오프라인 검사는 1,132개 통과했습니다.

성능 변경과 비교 조건
--------------------

인물 범위가 확정된 후속 질문은 기존의 선택적 scoped_identity 경로를 새 품질 코드에서
재검증했습니다. 새 코드인 verified_source_search는 첫 검색 결과가 실제로 한 건이며
닫힌 선물/날짜 질문에 해당할 때만 기존 추출형 초안을 최종 독립 검증에 먼저 제출합니다.
검증이 직접 답변으로 승인한 경우에만 중복된 중간 계획을 생략합니다.
여러 후보를 잘라 한 건으로 만들지 않으며 원문을 줄이지 않습니다.
거절·문맥·입력 범위 변경·복합 조건에서는 기존 경로로 돌아갑니다.
새 설정은 기본 비활성이고 비교 도구의 명시적 선택으로 실행합니다.

기준과 후보 양쪽에 같은 품질 수정·기존 통합 제안·입출력 정리를 적용했습니다.
최종 비교는 기준에 scoped_identity와 verified_source_search를 더한 조합의 효과이며,
별도의 단일 요인 예비 비교도 원자료에 보존했습니다.
스레드 8, 생성 배치 스레드 24, f16 KV를 사용했습니다.
CPU는 양쪽 모두 가중치 재배치를 끄고 측정했습니다.

첫 질문은 해석 캐시 및 생성 서버의 앞선 프롬프트 상태를 비웠습니다.
각 사례 준비 실행을 제외하고 기준·후보 순서를 교대해 5회 측정했습니다.
모델 로딩, 합성 DB 준비, 앞선 대화 준비, 질문 처리 시간을 구분합니다.
CPU의 준비 대화와 DB는 검증된 GPU 실행에서 가져온 것이며 CPU 자체 준비 시간과
혼동하지 않습니다. GPU 탑재 PC에서 CPU를 강제했으며 실제 GPU 없는 환경은 미검증입니다.
다른 앱을 유지한 16GB 환경으로, 시스템 여유 RAM 부족 및 장치 전체 VRAM의
다른 앱 사용량 변동도 원자료에 기록합니다.

실패·제외 후보의 보존
--------------------

* 정확 입력 선별 재사용: GPU 5개 예비 사례 모두 캐시 적중 0회, 유의미한 개선 없음.
* 배치 8: 긴 질문 약 88.6→51.1초였으나 무관한 제주 참석 충돌 사실을 추가해 수동
  품질 검사에서 탈락. 자동 검사 통과를 덮어쓰지 않고 별도 판정 파일로 보존했습니다.
* q8 KV: 과거 실패 검증 재확인 7/8, 정상 답변 거절 잔여 1건으로 제외했습니다.
* CPU 배치 스레드 8: 24보다 느려 제외했습니다.
* CPU 가중치 재배치 끄기: N=1에서 private commit 약 7600→4400MiB,
  속도 이득 없음. 이후 양쪽 비교 조건에 공통 적용했습니다.
* 이전 CPU 첫 질문 5회 실행은 새 최적화에 의해 중도 대체됐습니다.
  취소 원자료를 보존하며 완료된 N=5로 표시하지 않습니다.
* CPU 후속 기준은 300초 시간 초과를 관측했습니다. 이를 정상 답변 시간이나
  기준 중앙값으로 삼아 개선율을 계산하지 않습니다.

결과 열람과 재실행
------------------

``scripts/summarize_identity_optimization.py``는 저장된 결과만 읽어 JSON과
읽기 전용 HTML 검토표를 만듭니다. HTML 열기·새로고침은 모델을 실행하지 않습니다.
각 실행 폴더의 ``answers.html``에서 답변·원문·인용을 직접 비교할 수 있습니다.
실제 측정은 ``scripts/run_latency_goal.ps1``에서 기본적으로 계획만 표시하고,
명시적 ``-Execute`` 옵션이 있을 때만 실행합니다. 일반 서버 임시 종료는
별도 ``-PauseOrdinaryModels`` 옵션을 선택할 때 수행하고 종료 뒤 복구합니다.

다른 후보·입력 범위를 동일한 입력이라고 간주해 재사용하지 않았습니다.
순위 계산이나 전면 C++ 전환으로 이 모델 추론 비용이 사라진다고 해석하지 않습니다.

CPU 후속 확인과 남은 병목
-------------------------

후보만 준비 실행 뒤 N=5 확인했습니다. 5/5 정상 답변·근거 검증 완료,
중앙값 153.39초·최댓값 155.93초, Qwen 4회입니다. RAM 최고 5874.63MiB,
private commit 최고 4453.20MiB, 시스템 여유 RAM 최저 239.70MiB입니다.
GPU 준비 대화를 가져온 조건이며 CPU가 직접 준비한 대화 시간과 구별합니다.
기준의 300.10초 ReadTimeout 1회는 정상 완료 기준 중앙값으로 사용하지 않습니다.
CPU 후속의 상대 개선율, 20% 달성, 기준 대비 메모리 5% 통과를 산출할 수 없습니다.
CPU 후속 자체는 여전히 60초를 넘습니다.

긴 본문도 같은 CPU 조건에서 기준·후보 각 1회 별도로 대조했습니다.
후보 300.036초·기준 300.040초에 모두 CHAT_TIMEOUT으로 실패했습니다.
답변과 최종 검증을 완료하지 못해 품질 통과·정상 답변 중앙값·개선율을 산출하지 않습니다.
실패 선별이므로 5회로 확대하지 않았습니다. 이 실패도 원자료와 검토표에 보존했습니다.
따라서 전체 사례에서 시간 초과 0건이라는 안정성 조건도 충족하지 못했습니다.

후보의 단계별 모델 시간 중앙값은 질문 해석 11.24초, 관련성 선별 28.20초,
중간 제안 76.11초, 독립 검증 37.35초였습니다. 단계 중앙값들의 합은 전체 중앙값과
반드시 같지 않습니다. 남은 큰 비용은 문맥을 포함한 중간 제안과 최종 검증입니다.

직접 실행 예시
--------------

PowerShell에서 아래 명령은 계획만 표시합니다. 실제 실행하려면 마지막에
``-Execute``를 추가합니다. 일반 모델 서버의 임시 중지·복구가 필요한 경우에만
``-PauseOrdinaryModels``를 함께 추가합니다. 다른 앱과 개인 DB는 사용하지 않습니다.
기존 실행 폴더를 덮어쓰지 않도록 매번 새 RunName을 지정합니다.

.. code-block:: powershell

   Set-Location C:\development\Personal-Memory-Agent\.local\latency-validated-drafts
   $options = @{
       Placement = 'gpu'
       PlanningBaseline = $true
       CompactJson = $true
       CompactReview = $true
       SharedCompactFormats = $true
       ScopedIdentitySearch = $true
       VerifiedSourceSearch = $true
       ColdInterpretations = $true
       FixtureSplit = 'development'
       Cases = @('dev_fact', 'dev_date')
       Samples = 5
       GenerationBatchThreads = 24
       AnchorTemplates = '.local/latency-goal/identity-reuse-gpu-pilot/gpu/results.json'
       SeedTemplate = '.local/latency-goal/identity-reuse-gpu-pilot/gpu/synthetic-seed.db'
       PythonExe = 'C:/development/Personal-Memory-Agent/.venv/Scripts/python.exe'
       RunName = ('user-first-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
   }
   ./scripts/run_latency_goal.ps1 @options

CPU는 ``Placement='cpu'``와 ``DisableCpuRepacking=$true``로 바꿉니다.
반복 요청은 ``ColdInterpretations`` 항목을 제거하고 ``InterpretationReuse=$true``로
지정합니다. 두 모드는 섞어 같은 첫 질문 통계로 표시하지 않습니다.
이는 별도 합성 성능 도구이며 공식 메인 평가를 실행하지 않습니다.

입출력 정리와 계산 캐시: CPU·GPU 재비교
======================================

최종 상태 · 2026-10-22
----------------------

승인된 CPU·GPU 재비교를 완료했습니다. 단순 질문에서 속도 개선은 관측했지만
품질 회귀·CPU 목표 미달·일부 RAM 증가로 연구용 후보를 기본 설정에 채택하지 않았습니다.
GPU 단순 질문의 10초 달성과 전체 프로필의 품질·안정성 통과를 구분합니다.
기존 품질 실패에도 성능 비교와 추가 최적화를 진행하라는 사용자 요청으로 재개했습니다.
이전 인용·답변 완결성 보고서는 ``docs/answer_integrity_results.rst``에 보존합니다.

비교 기준
---------

* 작업 브랜치: ``codex/first-response-cpu-gpu``. 시작: ``daaae1c``.
  입출력 정리 구현: ``b9b8728``. 계산 캐시 선택 구현: ``4f0c80d``.
  반복 비교의 양쪽 해석 재사용 조건 정렬: ``cc6fc9c``.
* 기준은 앱 기본값이 아니라, 앞선 실험에서 사용한 통합 중간 제안·원문 사실/날짜 초안·
  제한된 추가 검색·명시적 문맥 바로가기 프로필입니다. 기준과 후보에 같은 품질 수정을 적용했습니다.
* 생성 가중치 Qwen3-8B Q4_K_M, 임베딩 BGE-M3 Q8_0, 설치된 llama.cpp를 유지했습니다.
  모델 교체·다운로드·검증 임계값 완화·원문 축약·후보 잘라내기는 하지 않았습니다.
* 첫 요청은 매번 해석 캐시와 생성 서버의 이전 프롬프트 슬롯을 비웁니다.
  모델 로딩, 합성 DB 색인, 준비 실행은 응답 시간과 분리했습니다.
* 준비 실행 후 사례별 기준·후보 5회이며 실행 순서를 교대했습니다.
  CPU와 GPU는 순차 실행하고 다른 앱은 유지했습니다. 개인 DB는 읽지 않았습니다.
* 후속 질문은 GPU에서 생성해 검증한 같은 합성 앞선 대화를 공유합니다.
  CPU가 그 앞선 대화를 직접 생성하는 데 성공했다고 해석하지 않습니다.

변경과 제한
-----------

``-CompactJson``은 JSON 구분자 사이의 불필요한 공백만 없앱니다.
원문 문자열 내부의 공백·줄바꿈·필드 값·후보 순서와 전체 원문은 보존합니다.

``-CompactReview``는 독립 검증 출력의 설명문과 중복 기록 ID를 생략합니다.
주장 지지·관련성·오류 종류·질문 충족·한계 설명의 적절성·인용 구간 판정은 유지합니다.
고유한 원문 구간에서 기록 ID를 복구하며 최종 검증 모델 호출은 매 요청 새로 수행합니다.
설명문이 줄어 상세한 판단 이유를 읽기 어려워지는 단점이 있습니다.
서버가 채운 중립적인 표시를 모델이 직접 작성한 설명처럼 보여주지 않습니다.
이 변경이 모든 미관측 질문에서 품질을 보존한다고 보장하지 않습니다.

``-GenerationCacheType q8_0``은 생성 서버의 K/V 계산 캐시 정밀도만 바꿉니다.
가중치 양자화 변경이 아니며 수치 계산은 f16 캐시와 다릅니다.
별도 실행군 비교이므로 순서·시스템 상태 영향이 남습니다.
GPU 결과를 CPU 결과에 그대로 적용하지 않습니다.
외부 서버나 임베딩 서버 옵션을 변경하지 않습니다.

이 옵션들은 명시적 연구용 실행에서만 켜집니다. 앱 환경 변수·기본 설정은 유지했습니다.
API 응답 구조와 DB 스키마도 유지했습니다.

제한으로 실패했습니다. 복합 질문은 둘 다 정답이었지만 기준 230.18초에서 후보
249.81초로 약 8.5% 느려졌습니다. CPU 복합·후속의 5회 개선 검증은 완료하지 않았고,
이 선별 실패를 20% 개선으로 집계하지 않습니다. 복합 질문은 양쪽 모두 표시용 검증
HTTP 호출에서 약 10초 오류가 있었으며, 독립 근거 검증을 통과한 답변이 반환됐습니다.

f16 캐시의 GPU 후보 추가 확인은 단순 질문별 20회, 총 40개 답변이 모두 통과했습니다.
사실 중앙값 / 최댓값은 8.43 / 8.90초, 날짜는 8.12 / 8.33초였습니다.
후보 단독 확인이므로 기준과 20회 교대한 비교로 표현하지 않습니다.

메모리와 병목
-------------

단순 사실 CPU에서 입력·출력 정리 전후 Qwen 3회·BGE 1회로 호출 수가 같습니다.
CPU 후보의 단계 중앙값은 질문 해석 약 14.02초, 중간 제안 약 30.77초,
독립 검증 약 33.89초입니다. 단계 중앙값을 합산해 전체 중앙값이라고 표현하지 않습니다.
검증 출력은 이 사례에서 112토큰에서 51토큰으로 줄었지만 원문 입력 처리 비용은 남습니다.
검색 순위 계산은 이 작은 합성 자료에서 밀리초 미만으로 모델 계산보다 훨씬 작습니다.
대량 DB 전체에 대한 새로운 순위 계산 벤치마크로 해석하지 않습니다.

GPU 후속 질문은 Qwen 11회·검색 2회가 남아 관련성 판단과 추가 검색이 지연을 만듭니다.
캐시가 없는 첫 질문을 동일 입력 반복 캐시의 속도로 대신 보고하지 않습니다.

RAM은 관측한 프로세스 트리의 작업 집합, private commit은 해당 예약량,
VRAM은 장치 전체 사용량입니다. 다른 앱·운영체제의 사용량이 섞이며 RAM과 VRAM을 더하지 않습니다.
샘플 관측이므로 모든 순간 피크를 포착한다는 보장은 없습니다.
CPU 강제 실행은 실제 GPU가 설치된 PC에서 오프로딩을 모두 끈 결과입니다.
물리적으로 GPU가 없는 환경의 검증은 하지 않았습니다.
CPU 측정 중 여유 RAM이 약 84MiB까지 줄어든 요청도 있었습니다.
긴 CPU 후속 질문의 실패 측정에서는 약 38MiB까지 줄었습니다.
GPU 후속 질문의 관측 RAM 피크는 후보가 기준 대비 5%를 넘었으므로,
이 항목을 메모리 제한 통과로 표시하지 않습니다.

다음은 첫 요청 본 측정 5회의 관측 피크이며 단위는 MiB입니다.
로딩·준비 실행의 피크는 이 표와 별도로 원시 결과의 ``startup`` 등에 보존했습니다.

후속 측정·품질·최종 판정
-----------------------

f16 캐시·입출력 정리 결합 후보의 실제 답변은 기존 노출 사례 13/16을 통과했습니다.
동명이인 모호성의 잘못된 승인, 원문 속 지시로 인한 불필요한 재질문이 남았고,
정답 이유를 포함한 답변이 부가 문장과 인과 검사 때문에 전체 거절되는 실패도 나왔습니다.
원문에는 ``진주 방문은 취소했다. 도로 통제 때문이다.``가 있었습니다.
단순한 표현 변화가 모델 선택·문장 구성을 바꿀 수 있으므로,
입출력 정보가 보존된다는 사실만으로 종단 품질 불변을 주장하지 않습니다.

q8_0 캐시도 같은 실제 답변 13/16이었으나 별도 검증 시험에서 정상 답변 2개를
추가로 잘못 거절했습니다. f16은 정상 4개 승인·변조 4개 거절, q8_0은 정상 2개
잘못 거절·변조의 잘못된 승인 0건이었습니다. q8_0의 GPU 5회·20회 확대를 제외했습니다.
초기 단순 GPU 1회 7.44초·7.22초는 품질 탈락 후보의 선별 수치일 뿐 최종 속도가 아닙니다.
검증 시험의 관측 장치 VRAM은 f16 7726MiB에서 q8_0 7032MiB로 줄었으나 품질이 탈락했습니다.

기존에 노출된 품질 자료의 재실행은 새로운 독립 확인 자료로 부르지 않습니다.
CPU 5회 최댓값을 전체 요청의 P95 보장으로 표현하지 않습니다.

같은 실행 안의 이유 질문 대조에서도 기준은 14.74초에 정답을 반환했지만,
후보는 20.31초에 근거 부족으로 거절했습니다. N=1 재현 검사이며 새로운 독립 확인은 아닙니다.
기존 비정리 프로필의 과거 14/16과 이번 결합 후보의 13/16은 동일 시점의 16개 전체
교대 비교가 아닙니다. 해당 이유 질문의 기준·후보 대조는 이번에 별도로 완료했습니다.

유지 판정에는 위 ``repeat-paired-five`` 실행만 사용했습니다.

확인 범위와 남은 작업
---------------------

초기 ``compact-json-gpu-screen``·``compact-review-gpu-screen``은 각 옵션을 따로 비교한
개발 사례별 N=1 선별입니다. 둘 다 네 개발 사례를 통과했으나 이 수치를 5회 개선율이나
전체 품질 통과로 사용하지 않았습니다. 별도 검증 시험·결합 품질 검사에서 탈락한 후보도
모든 원시 결과와 답변 검토표를 보존했습니다. 집계 JSON은 총 15개 실행을 포함합니다.

오프라인 검사는 최종 1043개 통과, 기존 Starlette 경고 1개였습니다.
테스트 임시 폴더는 작업 폴더 안에 지정했습니다. 실제 모델이 필요한 실험과 별도로 실행했으며,
공식 메인 평가는 실행하지 않았습니다. 제품·평가 소스·네이티브 확장 해시는 각 측정 동안 유지됐습니다.

일반 모델 서버 8081·8082는 최초와 같은 설정으로 복구했고 건강 확인 모두 HTTP 200이었습니다.
비교에서 의미 없는 명령행 끝 공백은 무시했습니다. 실험 서버 프로세스는 0개였습니다.
기본 작업 폴더는 ``codex/response-latency-recheck`` / ``8cb40f5``의 깨끗한 상태를 유지했습니다.
실험 ``.local`` 사용량은 약 17.95GiB, 디스크 여유는 약 17.17GiB였습니다.

다음 채택 전 우선순위는 검색에서 동명이인의 양쪽 근거를 잃지 않는 것과,
정답 이유를 포함한 답변 전체가 과도하게 거절되는 문제의 보완입니다.
새로운 독립 자료를 먼저 고정한 뒤 기존 실패와 함께 통과해야 합니다.
성능 측면에서는 긴 질문의 관련성 판단·추가 검색 호출과 CPU의 원문 입력 처리 비용이 남았습니다.
이번 추가 최적화에 C++ 확대·모델 변경·검증 완화는 사용하지 않았습니다.

사용자가 실행하고 확인하기
--------------------------

이 작업 폴더 PowerShell에서 다음 명령은 계획만 표시합니다::

    Set-Location 'C:\development\Personal-Memory-Agent\.local\latency-validated-drafts'
    ./scripts/run_latency_goal.ps1 -Placement gpu -PlanningBaseline -CompactJson -CompactReview -ColdInterpretations -Samples 5 -FixtureSplit development -Cases @('dev_fact','dev_date') -GenerationCacheType f16 -GenerationBatchThreads 24 -PythonExe C:\development\Personal-Memory-Agent\.venv\Scripts\python.exe -PauseOrdinaryModels -RunName my-compact-first

명시적으로 ``-Execute``를 붙여야 합성 모델 측정이 시작됩니다.
``-Placement cpu``는 CPU 강제 실행입니다. 각 실행은 새 RunName을 사용합니다.
``-GenerationCacheType q8_0``은 별도 계산 캐시 실험이며 CPU에는 현재 권장하지 않습니다.
동일 전체 입력 재사용은 ``-ColdInterpretations``를 빼고 ``-InterpretationReuse``를 넣습니다.
이 경우에도 서버의 이전 프롬프트 슬롯은 요청마다 비우므로 완전히 따뜻한 네이티브 캐시 실험은 아닙니다.
실제 대화가 달라지면 같은 질문 문장만으로 해석 캐시가 재사용된다고 보장하지 않습니다.

결과는 ``.local/latency-goal/<RunName>/<cpu 또는 gpu>/``에 저장됩니다.
``answers.html``은 답변·전체 원문·인용 구간·검증 과정을 보여주는 읽기 전용 검토표입니다.
열거나 새로고침해도 모델·공식 평가가 실행되지 않습니다.
``results.json``에는 시간·메모리·호출별 계측·소스와 모델 해시가 있습니다.
처리 중 ``cancel.request`` 파일을 해당 cpu/gpu 폴더에 만들면 요청 경계에서 중단하고 서버를 복구합니다.

이번 결과 모음은 ``.local/latency-goal/compact-review-index.html``입니다.
첫 요청·반복·품질 실패·시간 초과의 답변 검토표와 원시 결과를 각각 연결합니다.
정리된 수치·모델/실행 설정·해시·호출별 통계는 ``docs/compact_inference_results.json``에 있습니다.

공식 메인 평가, 기본 모델 교체, 기본 브랜치 병합·푸시는 수행하지 않습니다.

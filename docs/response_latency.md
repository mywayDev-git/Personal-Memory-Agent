# 응답 지연 계측과 비교

기준 커밋은 `5a57d39`다. 원문 의미 보존과 검색 관련성 수정 후 전체 Python
327개, 합성 브라우저의 검색 근거 표시, 다국어 설명·강조 검사를 통과했다.
`codex/multilingual-search`에 먼저 커밋·푸시하고 `codex/response-latency`를 분기했다.

## 계측 계약

`snapshot.performance.profile`은 선택 메타데이터다. 기존 응답 필드는 유지한다.
각 단계는 호출·실패 횟수와 inclusive/exclusive 초를 제공한다. 포함 시간은
부모·자식이 겹치므로 합산하지 않는다. 전체 요청은 외부 벽시계로 측정한다.
HTTP 호출은 경로·단계·상태·시간과 허용된 토큰 수만 기록한다. 질문, 원문,
모델 출력, 오류 메시지, 인증 정보는 성능 메타데이터에 포함하지 않는다.

대화 성공·실패·취소 모두 성능 스냅샷을 저장한다. 최종 저장 단계의 DB 메타데이터는
트랜잭션 커밋 직전까지이며, 커밋을 포함하는 시간은 평가 벽시계와 진단 콜백에서
관측한다. 계측은 요청마다 분리되며 관련성·답변 생성·독립 검증을 생략하지 않는다.

## 최초 진단

기존 앱은 그대로 유지했고 별도 18081/18082 포트의 CPU 서버와 합성 DB만 사용했다.
GPU는 RTX 3060 8GB 중 기존 앱이 약 7.6GB를 사용하므로 동시 실험을 시작하지 않았다.

새 CPU 기준선의 첫 답변 준비 실행은 약 87.7초였다. HTTP 관측상 생성 호출 7회가
약 87.1초, 토큰 계산 10회가 약 0.31초, 임베딩 1회가 약 0.07초였다.
이는 단일 준비 실행이며 중앙값이나 최종 성능 개선의 근거가 아니다. 토큰 계산만
줄여서는 20% 단축을 달성하기 어렵다. 생성·관련성 배치·표시 검토를 우선 비교한다.

## 안전한 실행

실험 데이터와 모델은 `.local/response-latency/`에 둔다. 모델 파일은 Git에 넣지 않는다.
별도 서버는 실험이 소유한 프로세스만 종료하며 개인 DB나 기존 앱을 재시작하지 않는다.
90개 다국어 평가에서는 새 질문 이해를 실행한다. 재생 결과는 지연 측정에 사용하지 않는다.
모델 교체는 품질과 속도 평가를 모두 통과한 뒤 선택하며 실제 개인 DB 전환은 별도 작업이다.

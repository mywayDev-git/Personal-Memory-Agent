# Personal Memory Agent — 사용자 행동 변수 및 테스트 설계 명세

목적: 사람들이 Personal Memory Agent에 어떤 기록을 남기고, 어떤 방식으로 과거 기록을 검색하며, Agent와 어떻게 대화하는지 예상 가능한 상황을 최대한 체계적으로 도출하고, 이를 Codex가 자동으로 테스트할 수 있도록 구성합니다.

단순히 기능이 동작하는지 확인하는 것이 아니라 사용자의 다양한 표현, 불완전한 정보, 기록 간 충돌, 검색 누락, 잘못된 근거, 대화 맥락 오류까지 검증하는 것이 목표입니다.

현재 프로젝트에서 계획한 구조를 기준으로 다음을 가정합니다.

- 기록 입력: 사용자가 직접 기록하거나 대화 중 저장을 명시적으로 요청하고, 허용된 자동 저장 정책에 따라 기록을 생성합니다.
- 검색: 검색 버튼을 통한 명시적 검색과 Agent가 대화에 필요한 과거 기록을 조회하는 내부 검색을 구분합니다.
- Agent 대화: GPT처럼 일반적인 대화도 가능하되, 개인 기록이 필요한 질문에는 기록과 기존 대화 맥락을 활용합니다.
- 근거 우선: 사용자 기록을 참고했다면 출처를 표시하고, 근거가 부족하면 추측으로 확정하지 않습니다.
- 애매한 질문: 기록과 대화 맥락으로 의미가 명확해지면 바로 답하고, 복수의 해석이 실질적으로 남는 경우에만 되묻습니다.

### 특히 검증해야 하는 검색어 확장

검색어를 자동으로 번역하거나 동의어로 확장하는 시스템에서는 다음을 별도로 검증해야 합니다.

- 원본 검색어가 항상 보존되는가?
- 확장된 단어가 원래 질문의 핵심 의미를 유지하는가?
- `C++`, 파일명, 함수명 등 식별자가 훼손되지 않는가?
- 공백이나 문장부호만 있는 확장을 거절하는가?
- 한영 왕복 번역이 부정확할 때 확장을 제한하는가?
- 잘못된 확장이 원본 검색 결과를 밀어내지 않는가?
- 확장 검색의 결과가 원문 검색보다 훨씬 약할 때 그 근거를 구별하는가?

왕복 번역은 검증 신호 중 하나로 사용할 수 있지만, 원래 단어로 돌아왔다는 이유만으로 의미 보존이 확정되는 것은 아닙니다.

# Part E. 실제 사용자 상황을 결합한 테스트

개별 변수만 테스트하면 실사용에서 발생하는 오류를 놓칩니다. 예를 들어 `오타`만 있는 검색은 성공하더라도 `오타 + 지난주 + 프로젝트 필터 + 대화 맥락`이 동시에 들어오면 실패할 수 있습니다.

# Part F. 테스트 결과를 어떻게 평가할 것인가?

## 18. 테스트 판정 항목

하나의 `PASS/FAIL`만 저장하면 원인을 분석하기 어렵습니다. 검색, 근거, 대화, 응답의 각 단계에 별도 결과를 남겨야 합니다.

| 평가 영역 | 주요 지표                          | 판단 기준                     |
| ----- | ------------------------------ | ------------------------- |
| 기록 입력 | 저장 성공률                         | 의도한 데이터가 올바르게 저장됐는가       |
| 정보 추출 | 필드 정확도                         | 시간·인물·상태가 정확한가            |
| 중복 처리 | 중복 판정 Precision/Recall         | 서로 다른 사건을 잘못 병합하지 않는가     |
| 검색    | Recall\@K                      | 정답 근거가 상위 K개 안에 있는가       |
| 검색 순위 | MRR, nDCG\@K                   | 관련 근거가 적절히 높은 순위인가        |
| 필터    | Filter Accuracy                | 범위·제외 조건이 지켜지는가           |
| 모호성   | Clarification Precision/Recall | 필요할 때만 되묻는가               |
| 문맥    | Reference Resolution Accuracy  | "그거", "두 번째" 등을 제대로 연결하는가 |
| 답변    | Answer Correctness             | 정답 사실과 일치하는가              |
| 근거    | Claim Support Rate             | 답변 주장이 근거로 뒷받침되는가         |
| 인용    | Citation Accuracy              | 정확한 출처와 위치를 표시하는가         |
| 부재 판단 | Abstention Precision/Recall    | 모르는 것을 적절히 보류하는가          |
| 보안    | Unauthorized Exposure Count    | 권한 없는 정보 노출 0건            |
| 삭제    | Deleted Data Exposure Count    | 삭제 후 비허용 데이터 노출 0건        |
| 성능    | p50·p95·p99 Latency            | 각 단계별 응답 지연               |
| 안정성   | Crash·Timeout Rate             | 요청 실패 및 장애율               |

`Recall@K`의 정답 근거는 단일 문서 ID뿐 아니라 필요한 근거 집합으로 정의할 수 있어야 합니다. 예를 들어 "왜 기술을 바꿨지?"는 최초 문제 기록과 최종 의사결정 기록을 모두 찾아야 정답일 수 있습니다.

# Part G. Codex 실행용 테스트 명세

## 20. 권장 테스트 데이터 구조

Codex가 자동으로 테스트를 실행하고 회귀 테스트까지 연결하려면 다음처럼 데이터 기반 테스트(JSON/YAML) + 실제 API 테스트 + 평가 스크립트 구조를 권장합니다.

테스트마다 다음을 구분합니다.

- `fixtures`: 미리 주입할 가상 기록과 관계
- `steps`: 저장, 검색, 대화, 수정, 삭제 등 실제 사용자 동작
- `expected`: 구조적으로 검증 가능한 결과
- `forbidden`: 절대 발생해서는 안 되는 결과
- `evaluation`: 정확 일치, 출처 검증, LLM 의미 평가 등
- `failure_codes`: 실패 원인 분류

예시 1 — 기록 저장부터 최신 상태 답변까지

```

id: LC-04
priority: P0
tags:
  - temporal
  - update
  - search
  - grounded_answer

fixtures:
  records:
    - id: record_001
      project: PMA
      content: "10월 10일 검색 정확도는 0.81이었다."
      event_time: "2026-10-10T10:00:00+09:00"

    - id: record_002
      project: PMA
      content: "10월 15일 검색 정확도는 0.89로 개선되었다."
      event_time: "2026-10-15T10:00:00+09:00"

steps:
  - action: query_agent
    message: "PMA 검색 정확도 최신 결과가 뭐야?"
    now: "2026-10-20T10:00:00+09:00"

expected:
  intent: memory_query
  required_evidence_ids:
    - record_002
  answer_facts:
    latest_accuracy: 0.89
    event_date: "2026-10-15"
  citation_ids:
    - record_002

forbidden:
  facts:
    - latest_accuracy: 0.81
  claims:
    - "검색 정확도가 0.95이다"

evaluation:
  retrieval: recall_at_k
  answer: structured_fact_check
  citation: source_verification

```

```
  answer: structured_fact_check

```

이 명세는 권장 테스트 계약의 예시입니다. 현재 프로젝트에 실제로 어떤 API와 모델이 존재하는지는 확인되지 않았으므로, Codex가 저장소를 조사한 뒤 실제 구조에 맞춰 필드명과 테스트 어댑터를 연결해야 합니다.

# Codex 작업 지시 — Personal Memory Agent 전체 사용자 행동 변수 테스트 구축

## 1. 작업 목표

현재 Personal Memory Agent 프로젝트를 분석하고, 사용자가 기록을 입력하고, 검색하고, Agent와 대화하고, 기억을 수정·삭제하는 전체 생명주기를 검증하는 테스트 체계를 구축하라.

이번 작업의 최우선 목표는 다음과 같다.

1. 개인 기록에 근거한 답변 정확도 확보
2. 검색 누락 및 잘못된 기록 선택 방지
3. 대화 맥락 유지 및 지시어 해석
4. 애매한 질문에 대한 정확한 판단
5. 시간 변화·기록 정정·상충 기록 처리
6. 잘못된 근거 인용 및 환각 방지
7. 기록 저장·수정·삭제의 일관성
8. 사용자 간 기록 격리 및 보안
9. 다양한 입력과 저사양 환경에서 안정적인 동작

- PF: 성능 및 안정성

## 8. 여섯 번째 단계 — 변수 조합 테스트

전체 Cartesian Product를 무조건 실행하지 말 것.

우선순위에 따라 다음 순서로 확장하라.

1. P0 단일 변수 전체
2. P0 핵심 사용자 시나리오
3. Pairwise 변수 조합
4. 위험도가 높은 3-way 및 4-way 조합
5. 랜덤 시나리오
6. Property-based 테스트
7. Metamorphic 테스트
8. 장기·반복·부하 테스트

Metamorphic 테스트 예시:

- 관련 없는 기록을 추가해도 기존 정답이 훼손되지 않아야 한다.
- 정확한 기술 식별자는 정규화·번역으로 변형되지 않아야 한다.
- 사용자가 날짜 조건만 바꾸면 다른 조건은 보존되어야 한다.
- 기록 순서를 바꾸어도 명시적인 시간적 사실은 유지되어야 한다.
- 접근 권한이 없는 기록은 검색 결과와 답변에 노출되면 안 된다.
- 기록을 삭제한 후에는 해당 기록이 검색·인용되지 않아야 한다.
- 원본과 의미가 동일한 질문 변형에 대해 핵심 사실은 일관되어야 한다.

단, 최신 정보 검색처럼 의도적으로 데이터 변경에 민감한 동작에는 적절한 사전 조건을 설정하라.

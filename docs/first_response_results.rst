첫 질문 응답 최적화 검증 기록
===========================

시제품과 사용자용 비교 도구를 구현했으나 새 프로필의 최종 채택은 보류했다.
GPU 10초·CPU 60초 목표를 달성했다고 판정하지 않는다. 일부 GPU 질문의 호출과 시간이
줄었지만 중요한 오답 승인과 처리 제한이 남아 조건부 후속 성능 검증으로 진행하지 않았다.

환경과 비교 조건
---------------

* 기반 커밋: ``31a2493``. 브랜치: ``codex/first-response-cpu-gpu``.
* 기존 작업 폴더 하나를 재사용하며 기본 프로젝트 체크아웃과 과거 실험 자료를 보존했다.
* i7-13700, RAM 16GB, RTX 3060 8GB. 다른 앱을 유지하고 개인 DB를 사용하지 않았다.
* 기준 모델은 Qwen3-8B Q4_K_M와 BGE-M3 Q8_0이다. 서버와 모델 파일 해시는 실행별 JSON에 있다.
* 기준 경로와 후보 경로는 같은 모델 서버를 순차 사용한다. 독립 검증 결과는 캐시하지 않는다.
* 모델 로딩·합성 자료 색인·준비 실행은 응답 시간과 분리한다. 각 첫 요청 전 해석 캐시와 서버 슬롯을 비운다.
* 측정 범위는 검색부터 독립 검증 및 응답 저장 완료까지이며 브라우저 표시 시간은 포함하지 않는다.
* CPU 강제 실행과 물리적으로 GPU가 없는 PC의 검증은 구분한다.

구현한 선택 옵션
---------------

문맥 해석·답변 후보 선별·추가 검색 판단을 하나의 구조화된 제안으로 묶었다.
실제 소비 시 질문·날짜·대화·원문·버전과 적용 대상 ID가 정확히 같아야 재사용한다.
추가 검색으로 근거가 달라지거나 출력이 잘못되면 해당 판단은 기존 경로로 돌아간다.
원문 속 지시가 포함된 자료는 통합 제안과 입력 중복 제거를 우회한다.

원문 전체와 모든 후보를 유지하면서 완전히 동일한 복사본만 참조로 바꾸었다.
검색 확장이 허용되지 않는 입력에서는 불필요한 확장 출력 생성을 제한한다.
명시적 날짜가 검증된 유일한 사건에는 원문 인용을 답변 후보로 제안할 수 있다.
원문 인용 후보도 독립 모델 검증을 새로 통과해야 답변으로 반환한다.
생성 모델이 답변을 만드는 경우에도 최종 검증은 별도 호출이다.

품질 검사에서 발견한 문제
----------------------

초기 검사에서 기준과 후보 모두 원문 속 명령을 구매 사실로 승인하는 문제가 있었다.
원문을 삭제하지 않고 사실 문장과 명령 구간을 별도 인용 ID로 구분하고,
명령 구간을 구매 사실의 근거로 승인하지 못하도록 보완했다. 이후 성능 비교는
이 공통 보완을 적용한 기준과 후보 사이의 비교다. 수정 전 커밋의 검증 동작과
완전히 같은 기준선이라고 표현하지 않는다.

통합 선별에서는 올바른 사실까지 거절하는 회귀가 발견되어 해당 입력 유형은
기존 판단과 기존 입력 형식을 유지하도록 했다. 단순히 빠른 거절을 개선으로 집계하지 않는다.

고정 채점 규칙과 원문 대조 검토를 분리한다. 개발용 충돌 사례의 동등한 불확실성 표현과,
이유가 없음을 명시하면서 확인된 산책 사실을 답한 경우에는 자동 채점의 한계가 있었다.
원래 자동 점수를 보존하고, 별도의 근거와 검토 기록을 남긴다.

모델·런타임 선별
---------------

* 8B 기준과 검색 확장 출력 제한 후보: 기존 검색 90개 비교에서 회귀 0개.
* Qwen3-4B-Instruct-2507 Q4_K_M: 검색 회귀 13개로 전체 교체 후보에서 제외.
* 같은 4B Q8_0: 검색 회귀 14개로 전체 교체 후보에서 제외.
* 두 4B 후보는 불필요한 CPU 전체 측정으로 진행하지 않는다.
* ONNX 후보는 고정 저장소 아티팩트에 ``genai_config.json``이 없고 실제 구성 로딩이 실패했다.
  외부 대형 가중치는 내려받지 않았으며 CPU·GPU 추론 속도를 측정한 것으로 표시하지 않는다.
  ONNX Runtime 자체의 Qwen3 미지원 판정과는 다르다.
* OpenVINO 후보는 제품 환경과 분리된 Python에 설치하고 필요한 고정 IR·토크나이저만 준비했다.
  실제 실행과 품질·성능 결과는 후속 측정란에 기록한다. 양자화도 다르므로 모델·런타임 조합의 비교다.

별도 확인 자료에서의 채택 차단
---------------------------

고정한 최종 확인용 ``final_pronoun``에서 기준과 후보 모두 동아리 친구의 후속 질문에
회사 동료의 직업까지 함께 답하고 독립 검증을 통과했다. 고정 근거 범위 위반이며 실제 품질 오류다.
기준에도 존재하므로 상대적인 회귀 검사는 통과할 수 있지만, 중요한 오답 승인 0건 조건에는 실패한다.
정상·변조 답변 묶음의 오답 승인 0건이 전체 답변 검사에서도 0건이라는 의미는 아니다.

이 자료를 보고 모델·해석 규칙을 맞추거나 기존 점수를 바꾸지 않는다. 이 GPU 후보의 최종 채택과
CPU 후보 전이는 차단한다. CPU 기준 경로 측정과 CPU 전용 런타임의 별도 호환성 선별은 구분한다.

품질 확인 결과
-------------

제품 처리 코드 ``8e4e4ce``를 고정한 GPU 비교다. 이후 변경은 결과 검토표·실행 기록·실패 시
측정 보존을 위한 도구 보완이며, 이 최종 자료에 맞춰 제품의 해석·프롬프트·모델을 고치지 않았다.

* 개발용 16개: 자동 검사 기준 13/16, 후보 14/16. 원문 대조 검토는 기준 15/16, 후보 16/16.
  기준의 긴 원문 1개는 ``CONTEXT_LIMIT``이다. 후보 오류는 0개다.
* 최종 확인용 16개: 자동 검사는 양쪽 11/16, 원문 대조 검토는 양쪽 13/16.
  동명이인 후속 질문의 잘못된 승인, 충돌 설명 부족, 긴 원문 처리 제한을 실패로 유지한다.
* 최종 충돌 답변은 “6명 또는 8명으로 확인됩니다”라고만 했다. 상충 기록과 정확한 인원 미확인을
  충분히 설명하지 않아 보수적으로 실패로 남겼다. 동명이인 오류와 처리 제한은 명백한 실패다.
* 이유 없음·날짜 미상 일부는 의미상 올바른 한계 설명을 했지만 상태값·표현 정규식 때문에
  자동 검사에 실패했다. 자동 점수를 고치지 않고 별도 원문 대조 기록에만 근거를 적었다.
* 전체 32개에서 중요한 오답 승인: 기준 1건, 후보 1건. 상대 회귀가 없다는 이유로 채택하지 않는다.
* 고정 검증 답변 8쌍은 중요한 변조 답변 승인 0/8이지만 정상 답변 거절 2/8이 남았다.
  이 작은 묶음의 통과 여부만으로 전체 답변의 안전성을 대신하지 않는다.

원문 대조 검토는 에이전트의 의미 검토이며 별도의 사용자 검토를 대신하지 않는다.
질문·답변·인용·조회 원문을 ``answers.html``에서 확인할 수 있다.

-----------------------------------

아래는 각 1회 관측이다. 중앙값·성능 채택·GPU 10초 달성의 증거로 사용하지 않는다.
콜 수는 Qwen 서버의 실제 생성 HTTP 요청 수다. 답변의 최종 독립 검증을 포함한다.

단순 사실의 후보는 질문 해석·통합 제안·독립 검증의 3회였다. 원문 인용 제안 조건에 맞지 않거나
추가 검색·별도 답변 생성·표시 검토가 필요하면 호출 수가 늘어난다.
후속 질문에서는 보수적 기존 경로 복귀와 추가 관계 검색 때문에 총 호출 수가 줄지 않은 사례도 있다.

별도 단순 사실의 RAM은 이 표본에서 약 8.3% 늘어 5% 한도를 넘었다. 1회 관측으로 원인이나
안정적인 증가율을 단정하지 않으며, 반복 메모리 채택 검사를 통과했다고 표시하지 않는다.
RAM은 모델 서버와 평가 프로세스의 working set 합, private commit은 해당 프로세스들의
private commit 합이다. 공유 페이지 중복과 표본 사이의 짧은 피크 가능성이 있으며,
장치 VRAM에는 다른 앱도 포함된다. 로딩 메모리는 각 원시 JSON의 ``startup.memory``에 별도 보존한다.

CPU 기준 및 실패한 메모리 옵션
--------------------------

CPU 강제 실행은 생성·임베딩 모두 ``--device none --no-op-offload --no-kv-offload``를 사용했다.
CPU 8스레드, 생성 프롬프트 처리 16스레드를 지정했다. GPU 없는 PC의 실물 검증은 하지 않았다.

* 재배치 환경값을 미지정한 기준 1회: 152.081초, 답변·근거 검사 통과.
  RAM 7987 MiB, private commit 8190 MiB, 최소 시스템 여유 RAM 201 MiB.
  Qwen 5회: 질문 해석 33.105초, 추가 검색 판단 36.803초, 문맥 해석 33.074초,
  최종 후보 선택 7.605초, 독립 검증 41.156초. BGE는 1회였다.
* ``LLAMA_ARG_REPACK=0`` 실험은 준비 실행과 첫 측정 모두 300초에 ``CHAT_TIMEOUT``.
  5회를 계속하지 않고 요청 경계에서 취소했다. 정상 답변의 중앙값으로 집계하지 않는다.
  첫 준비 실행의 RAM 8114 MiB, private commit 5004 MiB, 여유 RAM 최소 14.7 MiB.
* 재배치를 끄면 private commit은 줄었지만 이 관측에서는 RAM 감소나 응답 안정성이 확인되지 않았다.
  추가 검색이 발생해 관련성 판정 네 묶음에 약 165초가 소요됐다. 재배치 옵션만이 원인이라고
  단정하지 않는다. CPU 연산 차이로 모델의 검색 판단과 호출 수도 달라질 수 있다.
* 취소된 실행은 임시 서버를 정리하고 8081·8082 일반 서버를 복구했다. 두 health 검사가 통과했다.

동일 첫 질문의 CPU·GPU 기준 5회
----------------------------

동일한 ``dev_fact``와 동일 모델·코드·스레드 조건에서 모델 준비 실행 1회를 제외한 5회다.
해석 캐시와 이전 프롬프트 상태를 요청마다 비웠다. 재배치 환경값은 미지정이다.
이는 기준 경로의 장치 비교이며, CPU 최적화 전후 비교가 아니다.

OpenVINO·ONNX 최종 선별
---------------------

OpenVINO GenAI 2026.4.1.0과 고정 Qwen3-8B INT4 IR에서 CPU 실행·토크나이저·구조화 응답 API를 확인했다.
SDK의 단일 문자열 반환형을 잘못 가정했던 연결 코드는 한 항목 배치로 고쳐 실제 토큰 지표를 유지했다.
Windows 가상환경의 실행기와 실제 Python PID가 달라 자식 모델 프로세스를 포함하도록 메모리 집계도
보완했다. 이전 두 HTTP 오류 실행의 OpenVINO RAM 수치는 비교에 사용하지 않는다.

* 보완 후 고정 검증 답변 16개 처리 완료. 변조 오답 승인 1/8, 정상 답변 거절 1/8,
  생성·검증 처리 오류 2/16이었다. 동명이인의 직업을 바꾼 오답을 승인해 품질 선별에서 제외했다.
* 검증 묶음 처리 중 실제 모델 자식 프로세스를 포함한 RAM 7973 MiB, private commit 8464 MiB,
  장치 VRAM 579 MiB, 시스템 여유 RAM 최소 11.3 MiB. 프로세스 트리 관측은 완전했다.
* 이 값은 검증 전용 묶음이며 위 첫 질문 5회와 작업이 다르다. 전체 답변의 개선율이나
  메모리 5% 조건 통과로 계산하지 않는다. 품질 실패로 CPU 전체 답변 성능 비교에 진입하지 않았다.
* ONNX Runtime GenAI 0.18.0 후보는 필수 실행 설정 파일 누락으로 구성 로딩이 실패했다.
  CPU·GPU 추론은 미측정이며 런타임 자체의 Qwen3 미지원이라고 판정하지 않는다.

실험 패키지는 제품 Python과 분리했고 모델·런타임 파일 추가량은 약 11.24 GiB다.
기존 자료를 포함한 작업 폴더 ``.local`` 전체도 약 16.51 GiB, C 드라이브 여유는 약 18.65 GiB로
20 GiB·8 GiB 제한 안에 있었다. 모델 파일·실행기·런타임 DLL·질문 집합·합성 DB 해시를 보존했다.

반복 측정 및 최종 판정
--------------------

주 성능 사례는 개발용 ``dev_fact``·``dev_date``·``dev_pronoun``·``dev_compound``로
미리 정했다. 단순 사실·날짜·대명사 후속·복합 질문의 네 유형이다. 사전 계획은 각 가속 환경에서
준비 실행 뒤 기준/후보 순서를 교대해 5회 비교한다. 같은 네 유형의 동일 전체 입력
반복 조건은 두 경로에 해석 캐시를 켜 별도로 비교한다. 기본 모델의 90개 검색 선별과
32개 답변 품질 사례를 성능 사례 네 개로 대신하지 않는다.

최종 GPU 성능 후보가 선별되면 단순 사실·날짜의 20회 확인을 추가한다.
품질·오류·메모리 선별에서 탈락한 구성을 20회 속도 확인으로 구제하지 않는다.
사례 네 개의 결과를 모든 질문·모든 DB 크기의 응답 시간 보장으로 확대하지 않는다.

품질 선별에서 최종 후보가 없어 해당 후보의 CPU 이전, 전체 사례의 5회 채택 검사,
GPU 20회 최종 확인과 동일 입력 반복 5회 채택 검사를 생략했다. 미실행을 통과로 표시하지 않는다.
일부 GPU 1회 값이 10초 미만이어도 미리 정한 사례별 중앙값·품질·메모리 조건 통과가 아니다.
복합·후속 20% 개선과 반복 요청 악화 제한도 최종 통과로 판정하지 않았다.

오프라인 검사 952개가 통과했다. 새 프로세스 트리 집계는 모델 없는 실제 자식 프로세스로도 확인했다.
원문 변경·삭제 후 무효화, 잘못된 제안 복귀, 취소·시간 제한, 원문 지시 및 독립 검증 검사를 포함한다.
GPU 시작 실패·CPU 전환은 모의 실행기 검사로, 실제 취소·실패 복구는 이번 CPU·OpenVINO 실행으로
확인했다. 물리적으로 GPU가 없는 PC의 검증이나 공식 메인 평가를 수행한 것으로 표시하지 않는다.

남은 차단점은 후속 대명사에서 확인된 인물 역할을 끝까지 보존하는 것과 긴 원문 문맥 처리다.
현재 확인용 자료는 결과가 공개됐으므로, 후속 보완 시 새 독립 확인 자료를 먼저 고정해야 한다.

사용자가 실행하고 확인하는 방법은 ``docs/first_response_goal.rst``에 있다.
기본 실행은 계획만 표시하고 ``-Execute``가 있을 때만 모델을 구동한다.
공식 메인 평가는 이번 도구의 실행과 별개이며 자동 실행하지 않았다.
일반 서버는 승인된 측정 동안만 중단하고 매 실행 종료 시 원래 설정으로 복구한다.
기본 브랜치 병합과 앱 기본 모델 교체는 하지 않는다.

결과 파일
---------

* ``docs/first_response_results.json``: 내용 없는 성능 요약·해시·선별 결과.
* ``.local/latency-goal/first-response-quality-generation-stable``: 개발용 16개 비교와 원문 대조 기록.
* ``.local/latency-goal/first-response-holdout-frozen``: 별도 16개 비교·실패 기록·답변 검토표.
* ``.local/latency-goal/first-response-baseline-default-five``: CPU·GPU 기준 5회·메모리·단계별 원시 결과.
* ``.local/latency-goal/first-response-openvino-batched``: 실제 자식 프로세스를 포함한 OpenVINO 선별 결과.
* ``.local/final-first-response-tests.xml``: 오프라인 검사 결과.

기준 두 환경 집계의 보고서 인자 오류는 집계기에서 수정하고, 원시 결과를 다시 읽어 복구했다.
모델을 다시 실행하거나 이전 관측을 덮어쓰지 않았다. 취소·실패한 실행 자료도 보존했다.

Personal Memory Agent — 실행 진단 및 메모리·저장 수정 계획
작성일: 2026-11-06

범위
이번 변경: 새 실행의 실패 원인을 자세히 기록하고 화면에 표시한다.
다음 변경: 아래 순서로 메모리·저장 병목을 수정한다. 아직 구현하지 않았다.
기존 실행·판정·원문·요약·임베딩·산출물은 보존한다. 실제 모델 테스트는 사용자가 수행한다.

1. 이번에 적용하는 진단 v1

기록 위치
- 질문 실패: 새 실행 결과의 error_details. 기존 error/error_code/error_stage와 함께 보존.
- 실행 준비 등 실행 전체 실패: run.error_details.
- 요약 저장 실패: summary_attempts의 새 행에 error_details.
- 요청 실패 시 별도 파일: .local/baseline/runtime/request-errors.jsonl에 추가 기록.
- 원래 실행 내보내기에 질문별 상세가 포함된다.

기록 항목
- 진단 ID·시각, 실행/질문/원문 ID, 처리 단계, 요약 구간 번호.
- 생성 모델/임베딩 모델 구분, 토큰 계산/전체 입력 계산/생성/임베딩 구분.
- 질문 임베딩과 문서 임베딩의 목적 구분.
- 요청 경로, 실패 구간(요청 전/전송·응답 대기/본문 읽기/응답 해석).
- HTTP 상태, 소요시간, 기존 제한시간 300초, 중단·제한시간 만료 여부.
- 제한된 깊이의 하위 예외 이름·코드·syscall·메시지와 소켓 바이트 수.
- 요청 전후 서버 상태·모델·PID·포트·관측된 종료 코드/시그널.
- 요청 전후 시스템 여유 RAM 및 웹 프로세스 RSS/heap/external/ArrayBuffer.
- 요청·응답 크기만 기록한다. 새 진단 로그에 본문/프롬프트/헤더/인증키를 넣지 않는다.

원인 분류
연결 거부, 연결 끊김, 연결 시간 초과, 응답 시작 시간 초과, 응답 본문 시간 초과,
요청 전체 제한시간 초과, 사용자 중단, HTTP 오류, 서버 응답 JSON 오류, 준비 안 된 서버,
OS가 명시적으로 반환한 메모리/저장 공간 오류, 나머지 미확인 오류를 나눈다.
낮은 여유 RAM만으로 OOM을 확정하지 않는다. 세부 코드가 없으면 미확인으로 남긴다.

실제 실행 기록에서 열기 → 실패 질문 선택 → 실행 오류 상세.
인용·의미 분리 화면에서도 답변 없는 실패 질문을 선택하면 상세를 볼 수 있다.
이전 실행은 상세 원인 미기록이라고 표시한다. 과거 fetch failed를 추정 원인으로 덮어쓰지 않는다.
성공 요청에는 새 파일 기록을 추가하지 않는다. 진단 파일 쓰기 실패가 원래 오류를 가리지 않는다.
자동 재시도·서버 자동 재시작·추가 상태 확인 요청은 도입하지 않는다.
모델/프롬프트/토큰 예산/시간 제한/인용·의미 기준도 바꾸지 않는다.

2. 병목의 관측 근거

대상: RUN-1793881522278-ff3308, M0, 671개, 약 21시간 44분.
- 답변 생성 458개, 연결 오류 213개.
- 시스템 여유 RAM 관측 최저 11,419,648바이트. 다른 프로그램 영향도 포함된다.
- 웹 서버 RSS 관측 최고 1,485,287,424바이트.
- SQLite의 run JSON 길이 87,712,550바이트.
- 진행·자원 갱신 샘플 32,916개. update마다 전체 run을 직렬화해 저장하는 경로가 있다.
- 검색 단위마다 진행 갱신. 199개 전부 임베딩 캐시 적중인데 검색 862.9초 사례.
- UI는 실행 중 전체 run을 반복 요청한다.
- Store.recover는 시작 시 모든 run payload를 한꺼번에 읽고 파싱한다.
- artifactCache는 개수·크기 제한 없이 산출물을 유지한다.

지연을 DB·페이지 교체·브라우저·질문 임베딩으로 나눠 측정한 결과는 없다.
모든 연결 오류의 직접 원인이 메모리 부족이라고 단정하지 않는다.

3. 수정 단계 A — 진행 정보 경량화 (다음에 먼저 할 변경)

목표: 매 검색 단위마다 커다란 결과 전체를 저장·전송하는 경로를 제거한다.

저장
- 새 진행 정보 전용 저장 영역을 추가한다. 기존 runs 및 리뷰 테이블은 변환하지 않는다.
- 상태·질문 번호·처리 단계·최근 제한된 이벤트·최근 자원값만 작은 스냅샷으로 저장한다.
- 검색 단위 갱신은 시간 간격을 두고 합친다. 단계 전환·질문 완료·오류·중단·실행 종료는 즉시 반영한다.
- 첫 단계에서는 완료 질문/실행 경계의 전체 결과 저장을 유지하여 변경 범위를 제한한다.
- 실행 중 원본 결과는 현재 실행 객체를 기준으로 유지한다. 중단 시 오래된 DB 객체로 덮어쓰지 않는다.
- 재시작 시 마지막 완료 질문과 마지막 진행 정보를 구분하며, 진행 중 출력은 완료로 처리하지 않는다.

조회·화면
- 진행 상태 전용 API를 만든다. 전체 결과를 가져오지 않고 진행 표시를 갱신한다.
- 선택 질문의 새 결과/산출물이 생겼을 때만 그 질문을 별도로 가져온다.
- 다른 실행·데이터셋·필터·열린 기준·판정 초안·스크롤은 유지한다.
- 닫힌 탭/다른 페이지에서는 큰 결과 조회를 하지 않는다.

검증 기준
- 671개 규모 합성 실행에서 캐시된 검색 단위 갱신마다 전체 run 저장이 발생하지 않을 것.
- 큰 더미 산출물이 있어도 진행 응답 크기가 완료 질문 수·원문 길이에 비례해 증가하지 않을 것.
- 단계 전환/오류/중단/종료가 즉시 보이고 완료 결과가 유실되지 않을 것.
- 자동 의미 통과나 평가 결과 변경은 없을 것. 이전 DB payload와 산출물 해시는 동일할 것.
- 직렬화 횟수·누적 바이트·DB 저장 시간·진행 응답 크기·이벤트 루프 지연을 계측한다.

4. 수정 단계 B — 결과·요약 중복 저장 제거

목표: 새 실행 결과에는 산출물 ID와 작은 상태 요약을 두고 실제 내용은 산출물 한 곳에서 읽는다.

- 새 실행 저장 형식 버전을 도입한다. 기존 실행은 기존 읽기 경로로 유지한다.
- extraction/retrieval/answer의 본문·설정·요약 레코드를 질문마다 run에 중복 직렬화하지 않는다.
- 진행 중인 질문과 필요한 대화 맥락만 메모리에 유지한다. 완료 질문 본문은 필요할 때 읽는다.
- context 추출 캐시는 제한하고, 범위·원문 버전·모델·프롬프트 해시가 같은 산출물만 재사용한다.
- 질문별 결과를 추가 저장하는 영역을 검토하여 실행 전체 재직렬화도 줄인다.
- 산출물 저장과 결과 참조 갱신의 순서·원자성·실패 복구를 검사한다.
- 내보내기·비교·하이라이트·인용·검토 지문·후속 대화의 읽기 호환성을 함께 검사한다.

검증 기준
- 실제 모델 입력·원문 접근 범위·인용 좌표·기존 산출물 의미가 동일할 것.
- 새 실행의 큰 본문이 결과 목록/진행 응답에 들어가지 않을 것.
- 저장량·직렬화 바이트·프로세스 RSS를 같은 합성 작업에서 이전 단계와 비교한다.
- 기존 DB 일괄 변환/압축/청소/삭제는 하지 않는다.

5. 수정 단계 C — 시작·조회·화면 메모리 상한

- recover는 RUNNING/QUEUED인 실행만 DB에서 선택한다. 완료된 모든 run을 한 번에 로드하지 않는다.
- 실행 목록의 상태 집계는 작은 별도 요약을 사용한다. 기존 원본 payload는 그대로 보존한다.
- 파생 요약은 수동 판정/삭제·복원 변경 시 정확히 갱신한다. 과거 판정을 새 기준으로 재채점하지 않는다.
- 브라우저 산출물 캐시에 개수·크기 상한과 최근 사용 기준 퇴거를 둔다.
- 기억/검색 모아보기는 페이지 단위로 읽는다. 페이지를 열었다는 이유로 모든 실행을 펼쳐 읽지 않는다.
- 큰 내보내기에서 run과 산출물을 반복 복제하는 경로를 줄인다.

6. 순서와 실제 모델 검증

순서: 진단 v1 → 단계 A → 단계 B → 단계 C. 각 단계별로 이전 버전과 비교 가능하게 기록한다.
변경마다 가짜 모델·격리 DB로 정합성과 쓰기/전송량을 먼저 확인한다.
실제 모델 테스트는 사용자가 수행한다. 같은 문항·모델·프롬프트·토큰 예산을 유지한다.
캐시 준비 상태와 신규 요약 생성/재사용을 구분하여 비용을 비교한다.
성능 개선 수치를 미리 확정하지 않는다. 단계별 관측값으로 다음 조정을 결정한다.
진단 로그는 새 실패에서 생긴다. 과거 213개의 세부 원인을 소급 복구할 수는 없다.

변경하지 않는 범위
모델 크기/양자화/문맥 8192/기존 출력 예산/자동 재시도/원문·질문·정답/기존 실행·판정.
요약 사실 왜곡, 검색 정확도, 대화 지원 범위, 요약/원본 표시 정합성은 별도 품질 개선 과제로 남긴다.
